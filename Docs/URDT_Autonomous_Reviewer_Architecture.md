# Архитектура автономного ИИ-ревьюера проектов Unity на базе URDT
*(Autonomous URDT QA Reviewer Architecture)*

---

## 1. Миссия и концептуальное видение

### 1.1. Главная цель системы
Превратить **URDT (Unity Remote Debugging Transport)** в **автономного агента-испытателя и топологического ревьюера (Autonomous QA, Topology & GDD Reviewer)** с безусловным фокусом на **Unity-First Core**.

Агент работает как внешний интеллектуальный ревьюер, который:
1. **Подключается к любой запущенной игре / полигону Unity** (с протокольной расширяемостью в будущем на Unreal Engine и Cocos Creator благодаря отвязанному сетевому протоколу) с автоматическим реконнектом при перезапуске Play Mode.
2. **Строит полную Многослойную Топологическую Карту приложения (Runtime Graphify)**: исследует все экраны, окна, переходы, 2D/3D локации и состояния интерактивных элементов, находя тупики и недостижимые экраны.
3. **Автономно разбирается в управлении любой игры** по методу **Триангуляции** (чтение GDD + анализ текста/иконок на экране + активное микродап-прощупывание физики).
4. **Воспринимает мир и угрозы в триединстве источников** (описание в GDD + маячки `UrdtHazardTarget` + авто-детектор траекторий летящих коллайдеров).
5. **Взаимодействует с игрой в True Real-Time (60 FPS)** естественным многопальцевым вводом (Multi-Touch: независимые пальцы, зажатие газа + руление стиком, свайпы, слайсы, удержание сбора ресурсов, дозирование тяги).
6. **Осознанно реагирует на динамические угрозы через Micro-SLM** (падающий метеорит, снаряд, обрушение моста), анализируя контекст и выбирая осмысленное уклонение за 40–60 мс.
7. **Управляет снимками состояний (Save-State & Rollback Engine)**: делает снапшоты сохранений игры перед рискованными действиями и мгновенно откатывает мир при необходимости.
8. **Естественно проходит цикл Game Over и рестарта**: при гибели находит кнопки «Заново/Retry» в UI, тестируя реальный пользовательский путь.
9. **Сопоставляет происходящее с Дизайн-документом (GDD)** на трех уровнях абстракции (DoD чек-листы, контрактные инварианты, оперативные гипотезы).
10. **Генерирует автономный интерактивный HTML-отчет аудита** с визуализацией графа приложения, таймлайном событий и зафиксированными расхождениями с GDD.

### 1.2. Фундаментальный постулат: Only URDT (Никакого сырого компьютерного зрения в быстром контуре управления)
Система **полностью исключает сырое компьютерное зрение (Pixel Vision / ViT)** из быстрого контура управления:
- **Никакого захвата видеопамяти** на 500 МБ/с, никакого визуального шума и задержек рендеринга (33–50 мс).
- **Никаких галлюцинаций пиксельных координат**, присущих тяжелым мультимодальным моделям (VLM).
- Управление строится на **100% достоверном семантическом графе сцены**:
  - Маячки UI: `UrdtUiTarget`, `UrdtUiWindowTarget`, `UrdtUiSliderTarget`, кнопки.
  - Маячки механик: `Urdt2DModuleTarget`, `Urdt2DDraggableTarget`, `Urdt2DSlotTarget`, `Urdt2DInteractiveAreaTarget`, `Urdt3DTarget`, `UrdtWaypointTarget`, `UrdtHazardTarget`.
  - Поток физических дельт и событий по WebSocket / Loopback IPC с сетевой задержкой **< 0.5 мс**.

### 1.3. Главная миссия: Замыкание контура автономной ИИ-разработки игр (Closed-Loop AI Game Engineering)

Ключевое стратегическое предназначение системы URDT — **полностью замкнуть цикл автономной ИИ-разработки игр (Self-Validating Autonomous Game Loop)**.

До создания URDT автономная разработка игр искусственным интеллектом упиралась в непреодолимый тупик:
- ИИ-агент (AI Coder) мог сгенерировать C#-код механики, создать префабы и собрать проект через компилятор.
- Однако ИИ был **полностью слеп в рантайме геймплея**: он не мог проверить, кликаются ли кнопки, срабатывает ли физический Snap в слот, корректно ли отскакивает мяч, удобна ли чувствительность виртуального стика и не блокирует ли модальное окно прохождение уровня.
- Агенту требовался человек-тестировщик, который запустит сцену руками, пощупает геймплей и опишет баги текстом в чат.

**С внедрением URDT контур становится на 100% замкнутым и самодостаточным:**

### 2.1. Два обязательных сценария эксплуатации системы (Dual Execution Workflows)

Архитектура URDT спроектирована для безусловной поддержки **двух равноправных сценариев работы**:

#### Сценарий 1: Интерактивная работа в редакторе (Editor Dev & QA Mode)
- **Целевая аудитория:** Разработчик, тестировщик или локальный ИИ-агент (Antigravity / Cursor) в процессе активной разработки.
- **Инструментарий управления:** Официальный **Unity MCP Server** (инструменты `editor_play`, `editor_stop`, `eval`, чтение консоли и компиляция).
- **Поток работы:**
  1. ИИ-агент или разработчик инициирует сессию через команду `editor_play`.
  2. Внутри запущенного Unity Editor компонент `UrdtRuntimeBootstrap.cs` поднимает локальный сервер:
     - **Named Pipe** (`\\.\pipe\urdt_fast_ticker`) на Windows (или Unix Domain Socket на macOS/Linux) — выделенный ультра-быстрый канал для 60 FPS стрима кинематики L1 (< 0.05 мс).
     - **WebSocket-сервер** (`ws://127.0.0.1:9002`) — для передачи событий, снапшотов `MechanicStateSnapshot` и отчётов.
  3. Процесс `CoreAgent` подключается к запущенному Unity Editor, выполняет версионное рукопожатие (`Handshake`) и начинает непрерывное тестирование.
  4. **Устойчивость к Play Mode:** При остановке или перезапуске сцены (`editor_stop` $\rightarrow$ `editor_play`) CoreAgent не падает, а переходит в режим ожидания с авто-реконнектом. Как только сцена снова загрузилась — тестирование продолжается автоматически.
  5. Разработчик в реальном времени наблюдает за действиями агента в окне Game View или в локальном веб-дашборде (`http://localhost:3000`).

#### Сценарий 2: Полностью автономный CI/CD режим (Headless Standalone Pipeline)
- **Целевая аудитория:** Автоматические ночные сборки, конвейеры регрессионного тестирования (GitLab CI, GitHub Actions, TeamCity).
- **Инструментарий управления:** **Unity CLI** в пакетном режиме (`Unity.exe -batchmode`).
- **Поток работы:**
  1. CI-пайплайн запускает Unity через командную строку с **виртуальным дисплеем** (категорически запрещено использовать флаг `-nographics`, так как он обнуляет матрицы `CanvasScaler` и ломает `GraphicRaycaster`):
     ```bash
     Unity.exe -batchmode -force-vulkan -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 -projectPath "E:\Projects\URDT" -executeMethod UrdtTestRunner.RunHeadless -urdtPort 9002 -urdtPipeName "urdt_ci_9002" -urdtSessionToken "SEC_AUTONOMOUS_TOKEN_9002"
     ```
     *(Примечание: для Linux-раннеров запуск выполняется под `xvfb-run -s "-screen 0 1920x1080x24" Unity ...`, для Windows — с драйвером виртуального дисплея).*
  2. **Синхронизация старта (Handshake Probe):** CoreAgent опрашивает порт рукопожатия с экспоненциальным бэкоффом (до 60 сек), дожидаясь полной загрузки ассетов и инициализации движка.
  3. **Пакетный прогон по матрице тестов:** Агент автономно выполняет тестовые сценарии L3, сопоставляя поведение игры с инвариантами GDD.
  4. **Защита от зависаний (Graceful Shutdown):** При получении сигнала отмены от CI-раннера (`SIGTERM` / таймаут шага) агент гарантированно отправляет команду `EMERGENCY_RELEASE_ALL_POINTERS`, сбрасывает накопленный граф в файл `Docs/QA_Audit_Report.html` и завершает процесс Unity.
  5. **Коды возврата:** Завершение с кодом `exit 0` (все инварианты пройдены) или `exit 1` (обнаружены критические тупики, регрессии или падения игры).

## 3. Архитектура Unity-First Core и протокольная расширяемость (Hexagonal / Ports & Adapters)

### 3.1. Стратегический фокус: Unity-First Core
Вся текущая версия системы, глубокая интеграция маячков, инжектор ввода, безаллокационные диспетчеры и CI-раннер создаются со **100% фокусом на Unity Engine** (`com.davasko.urdt`).
Архитектура спроектирована по принципу **Ports & Adapters (Hexagonal)**: ядро `CoreAgent` изолировано от движкового SDK через стандартизированный сетевой протокол v2. Это оставляет чистый путь для подключения адаптеров под другие движки (Unreal Engine C++, Cocos Creator, Web) на дальнейших этапах развития платформы, исключая распыление инженерных ресурсов на текущем этапе.

## 4. URDT Wire Protocol v2: 4-слойный слепок состояния и Реактивная Шина Событий (Event Bus)

Протокол обеспечивает двусторонний обмен данными в реальном времени: от быстрой отдачи физических дельт до передачи глубокого дерева состояний механик и асинхронных событий маячков.

### 4.1. Четырехслойная модель данных протокола v2
1. **Пространственный слой (Dual Coordinates):**
   - `worldPos`: Мировые координаты $[X, Y, Z]$ в метрах (для 3D, физики и пространственной навигации).
   - `screenNormalized`: Нормализованные координаты $[u, v] \in [0.0 .. 1.0]$ (не зависят от разрешения и соотношения сторон).
   - `screenPixels`: Физические экранные пиксели $[X_{px}, Y_{px}]$ (для закона Фиттса и расчетных зон взаимодействия).
   - `frustumStatus`: Положение относительно камеры (`InView`, `Occluded`, `BehindCamera`).
2. **Физический и кинематический слой:**
   - `velocity`: Линейная и угловая скорость $[v_x, v_y, v_z]$.
   - `mass`, `isKinematic`, `currentContacts[]` (с какими коллайдерами соприкасается объект).
   - `forces`: Активные силы, импульсы и сопротивление среды.
3. **Событийный и динамический слой (Event & Hazard Buffer):**
   - Очередь недавних событий движка: `OnCollisionEnter`, `OnTriggerStay`, `OnSnapped`, `OnResourceMined`, `OnAnimationCompleted`.
   - **Динамические угрозы мира:** `activeHazards[]` (падающие метеориты, летящие снаряды, зоны урона с их таймерами падения/прилета).
4. **Контекст интерфейса и управления (UI & Control Context):**
   - Активное модальное окно (`activeModalWindow`), статус блокировки лучей (`blocksRaycasts`).
   - Состояние виртуальных стиков (`UrdtUiStickTarget`: отклонение $[-1.0 .. +1.0]$, центр, радиус, `deadZone`).
   - Активные каналы тача движка (`activeTouches`: какие пальцы сейчас физически прижаты).

### 4.2. Иерархическое дерево состояний механики (Mechanic State Tree)
Игра управляется не плоским списком векторов, а иерархическим деревом логических состояний. Корневой маячок механики (`Urdt2DModuleTarget` / `UrdtMechanicTarget`) генерирует структурированный срез `MechanicStateSnapshot`:

```json
{
  "mechanicId": "M01_SnapToSlot",
  "timestamp": 1726912345678,
  "lifecycle": {
    "phase": "RUNNING",                // "INIT" | "RUNNING" | "ANIMATING" | "PAUSED" | "COMPLETED" | "FAILED"
    "isBusy": false,                   // true, если идет катсцена/анимация и ввод заблокирован
    "busyReason": null,                // "ChestOpeningAnimation", "VictoryBanner", "DialogTransition"
    "timeInCurrentPhaseMs": 1450
  },
  "progress": {
    "current": 2,
    "target": 3,
    "normalized": 0.667,
    "score": 250
  },
  "entities": {
    "draggables": [
      {
```

### 4.5. Архитектура конфигурации и оптимизации маячков (Beacon Optimization Engine)
Чтобы игра не теряла кадры от оверхеда сериализации и аллокаций памяти (`GC Alloc`), внедрена 3-уровневая оптимизация:

1. **Битовая маска отслеживания в инспекторе (`UrdtTrackingMask`):**
```csharp
[Flags]
public enum UrdtTrackingMask
{
    None                = 0,
    PointerInput        = 1 << 0, // Click, Down, Up, LongPress, Hover
    DragAndDrop         = 1 << 1, // DragStart, DragMove, DragEnd
    SlotDocking         = 1 << 2, // HoverSlot, Snapped, Rejected
    ValueChanges        = 1 << 3, // Slider, Toggle, Dropdown, Text
    ScrollEvents        = 1 << 4, // ScrollStart, EdgeReached
    WindowLifecycle     = 1 << 5, // Open, Close, BackdropClick
    Triggers            = 1 << 6, // 2D/3D TriggerEnter, TriggerExit
    Collisions          = 1 << 7, // 2D/3D CollisionEnter, Impulses
    FrustumVisibility   = 1 << 8, // BecameVisible, BecameInvisible
    AnimatorEvents      = 1 << 9, // Mecanim state machine & cues
    SpineEvents         = 1 << 10,// Spine 2D animation cues & user events
    AudioEvents         = 1 << 11,// AudioSource & FMOD playback events
    All                 = ~0
}
```
2. **Динамическая ленивая активация по подписке (Lazy Subscription Wiring):**
   Если CoreAgent не подписался через `subscribe` на `physics_collision_*`, `spine_user_event` или `audio_clip_played`, C#-маячки **вообще не вызывают обработчики коллизий, аудио и эвенты скелета**, давая 0% оверхеда.
3. **Троттлинг и пороги нечувствительности (DeadZone Throttling):**
   Непрерывные события (`ui_scroll_delta`, `ui_slider_value_changed`) троттлятся до 20 Гц (не чаще 1 раза в 50 мс) и отсекаются, если изменение меньше 1% (`deltaThreshold < 0.01`).

### 4.6. Потокобезопасность, Dual-RingBuffer и тайминг-модель (`UrdtMainThreadDispatcher.cs`)
Входящие сетевые соединения (Named Pipe / WebSocket) в Unity работают в **фоновых системных потоках**. Любая попытка вызвать API движка (`transform.position`, `Physics2D`, `EventSystem.current`, `Animator`) напрямую из сокетного потока немедленно приводит к фатальному `UnityException: Can only be called from the main thread`.

Для гарантированной потокобезопасности, разделения потоков и полного устранения GC-аллокаций внедряется **`UrdtMainThreadDispatcher.cs`**:
1. **Архитектура независимого Dual-RingBuffer (Lock-Free MPSC):**
   - Вместо единого смешанного буфера используются два независимых предвыделенных кольца фиксированного размера (по 256 слотов):
     - **`MpscRingBuffer<UrdtUiCommand>` (UI Queue):** атомарно наполняется командами интерфейса из сети и **вычитывается строго в начале кадра `MonoBehaviour.Update()`** (клики, скроллы, фокусы, навигация).
     - **`MpscRingBuffer<UrdtPhysicsCommand>` (Physics Queue):** атомарно наполняется физическими воздействиями и **вычитывается строго в начале физического шага `MonoBehaviour.FixedUpdate()`** (силы, импульсы, свайпы твердых тел, отклонения виртуального стика).
   - **Политика переполнения (Overflow Policy):** При burst-наплыве команд (например, разгрузка очереди после SLM-инференса) применяется политика `DiscardOldestWithWarning`, фиксирующая предупреждение в телеметрии без падения движка.
2. **Тайминг-модель и устранение фазового рассинхрона (AC/DC Timing Alignment):**
   - Заявленная задержка Named Pipe (< 0.05 мс) относится исключительно к **межпроцессной передаче байт (IPC)**.
   - Физический отклик в Unity дискретизируется с шагом физики `Time.fixedDeltaTime` (по умолчанию 50 Гц / 20 мс). Если команда приходит между тиками физики, она применяется в начале следующего физического шага.
   - Каждая команда снабжена монотонным счетчиком ревизии мира (`worldRevision`) и флагом идемпотентности (`idempotencyKey`), предотвращающим повторное применение команды при сдвоенных вызовах `FixedUpdate`.

### 4.7. Двойной транспорт: Named Pipe (Fast Ticker) vs WebSocket (Full State)
Для оптимизации сетевых задержек на локальной машине применяется раздельный транспорт:
1. **Скоростной канал L1 Fast Ticker (< 0.05 мс):**
   - **Windows:** Локальный именованный канал `Named Pipe` (`\\.\pipe\urdt_fast_ticker`).
   - **macOS / Linux:** `Unix Domain Socket` (`/tmp/urdt_fast_ticker.sock`).
   - **Фиксированный бинарный фрейм (27 байт):** Передача потока координат и фаз тача осуществляется без упаковки в JSON. Полная спецификация байтового лейаута приведена в **Appendix A.1**.
   - Обеспечивает прямую межпроцессную передачу пакетов без накладных расходов стека TCP, исключая буферизацию алгоритма Nagle и давая стабильные 60 FPS без джиттера.
2. **Событийный канал Full State Push (WebSocket):**
   - Порт `ws://127.0.0.1:9002` с принудительным флагом `TCP_NODELAY`.
   - Передача структурированных конвертов (Envelopes) в формате JSON:
     - `CommandEnvelope` — сетевая команда от агента (см. **Appendix A.2**).
     - `StateEnvelope` — срез дерева состояний и телеметрия (см. **Appendix A.3**).
     - `ActionResult` — квитанция применения команды движком (см. **Appendix A.4**).
   - Передача дерева `MechanicStateSnapshot` (1 раз в секунду), асинхронные события маячков (`OnSnapped`, `OnWindowOpened`) и данные в живой веб-дашборд.

### 4.8. Zero-Allocation Path в горячих путях C#
Чтобы исключить периодические микро-фризы от сборщика мусора (`GC.Collect()`) в процессе непрерывного тестирования, маячки обязаны строго следовать стандартам Zero-Allocation:
1. **Безаллокационная физика со страховкой переполнения:**
   - Запрещено использование свойства `Collision.contacts` (создающего новый массив `ContactPoint[]` при каждом соприкосновении).
   - Маячки используют non-allocating API `Physics.GetContacts(ContactPoint[] buffer)` и `Physics2D.GetContacts(ContactPoint2D[] buffer)` со статическим предвыделенным буфером на 16 элементов.
   - **Страховка от переполнения:** Если возвращенное количество контактов `count >= 16`, маячок считывает оставшиеся контакты через пул массивов `ArrayPool<ContactPoint>.Shared`, предотвращая молчаливую потерю физических взаимодействий в сложных мешах.
2. **Безаллокационные слушатели событий (Static Relay Delegates):**
   - Категорически запрещено создание динамических лямбда-замыканий вида `button.onClick.AddListener(() => SendEvent(id))`, аллоцирующих скрытые замыкания в куче.
   - Все динамически подключенные кнопки направляются на единый статический метод `UrdtEventRelay.OnButtonClicked(int beaconId)` с передачей целочисленного ID маячка.
3. **Пул буферов для сериализации снимков:**
   - Вместо создания новых `new byte[]` в методе `CaptureState()` используются арендованные срезы памяти `ArraySegment<byte>` из `ArrayPool<byte>.Shared`.
4. **Троттлинг сканирования окружения:**
   - Сканирование окружающих физических тел `Physics.OverlapSphere` ограничено частотой 12 Гц (не чаще 1 раза в 5 кадров) с кэшированием результатов между вызовами.

## 5. Инструментарий авто-разметки и адаптации маячков (Auto-Instrumentation & Beacon Scaffolding)

Система URDT проектируется строго для **замкнутого цикла разработки собственных проектов (First-Party Closed-Loop AI Game Engineering)**. Модуль **`UrdtAutoInstrumentation.cs`** выполняет роль ассистента авто-скаффолдинга и линтинга сцены:

1. **Авто-детекция стандартных UI-элементов (Baseline Scaffolding):**
   - При старте сцены скрипт сканирует иерархию объектов:
     - Все стандартные `UnityEngine.UI.Button`, `Selectable`, `Toggle`, `Slider`, `Dropdown` $\rightarrow$ автоматически получают динамические прокси-маячки UI (`UrdtUiTarget`).
     - Объекты со стандартными коллайдерами и интерфейсами `IDragHandler`, `IPointerDownHandler` $\rightarrow$ получают базовые прокси интерактивности.
     - Текстовые поля `TextMeshProUGUI` и `Text` парсятся для семантического заземления (Grounding) на термины из GDD.
2. **Железное правило создания и адаптации маячков (Definition of Done):**
   - Авто-инструментация покрывает лишь типовой базовый интерфейсный каркас.
   - **Если механике не хватает специализированного маячка для полноценного тестирования (сложный 2D/3D драг, кастомная физика, нестандартная система ввода) — недостающий маячок ОБЯЗАТЕЛЬНО СОЗДАЁТСЯ разработчиком или ИИ-агентом (`Urdt2DModuleTarget`, `UrdtCustomMechanicTarget`, `UrdtHazardTarget` и др.) и адаптируется под новые вводные механики!**
   - Разметка механики контрактными маячками является обязательной частью приемочного критерия готовности (DoD) фичи. Ни одна механика не считается завершенной без актуальных маячков URDT.

## 7. Триединство восприятия мира и угроз (Triad World & Threat Perception)

Агент никогда не полагается на один источник информации об опасностях:

1. **Знание из GDD (GDD Level Spec):**
   - L3 извлекает из диздока: *«На 2-й минуте уровня падают метеориты с интервалом 5 сек»*.
2. **Явные маячки движка (`UrdtHazardTarget`):**
   - Если разработчик разметил опасности: маячок отдает точный радиус взрыва, тип урона и время до удара `timeToImpactMs`.
3. **Эвристический авто-детектор опасных тел (Dynamic Physics Detector):**
   - Если маячка нет (чужой проект): агент непрерывно сканирует все `Rigidbody` / `Collider` в радиусе 10 метров от игрока.
   - Если объект имеет тег `Hazard/Damage` ИЛИ вектор скорости $\vec{v}$ направлен в сторону персонажа со сближением за $< 1.0\text{ сек}$ $\rightarrow$ он автоматически квалифицируется как **критическая угроза**.

## 8. ДЕТАЛЬНАЯ АРХИТЕКТУРА УРОВНЯ L1: Многоканальный биоманипулятор

### 8.1. Архитектура каналов Multi-Touch (`pointerId: 0..3`)
На мобильных устройствах и в сложных играх действие редко выполняется одним пальцем.
В L1 встроен **Multi-Channel Touch Manager**, поддерживающий до 4 независимых каналов ввода:

```
                       ┌───────────────────────────────────────┐
                       │  L1 Multi-Channel Touch Manager (0..3)│
                       └───────────────────┬───────────────────┘
                                           │
         ┌───────────────────┬─────────────┴─────┬───────────────────┐
         ▼                   ▼                   ▼                   ▼
   [ Канал 0 ]         [ Канал 1 ]         [ Канал 2 ]         [ Канал 3 ]
   (Главный палец)     (Второй палец)      (Третий палец)      (Четвертый палец)
   - Руление стиком    - Кнопка газа       - Кнопка стрельбы   - Наклон камеры
   - Drag детали       - Удержание щита    - Сбор ресурса      - Pinch-зум
```

### 8.2. Структура команды низкого уровня (`L1CommandPacket`)
```typescript
interface L1CommandPacket {
  commandId: string;
  pointerId: number; // 0..3 (в Unity транслируется в 1..10)
  primitive: 'TAP' | 'DRAG' | 'SWIPE' | 'SLICE' | 'HOLD_EVENT_CONDITIONED' | 'CHARGE_AND_RELEASE' | 'CONTINUOUS_STEER_STREAM' | 'PINCH_ZOOM' | 'QTE_TIMED_TAP';
  
  targetBeaconId?: string;
  kinematicParams: {
    startScreenPixel?: { x: number; y: number };
    endScreenPixel?: { x: number; y: number };
    screenNormalized?: { x: number; y: number; isNormalized: boolean };
    waypoints?: Array<{ x: number; y: number }>;
    
    // Для непрерывных и условных примитивов:
    holdCondition?: {
      targetEvent?: string;      // "OnResourceMined", "OnLapCompleted", "OnFuelEmpty"
      predicateKey?: string;     // "chargeNormalized >= 1.0"
      maxTimeoutMs: number;
    };
    
    steerVector?: { x: number; y: number }; // Отклонение стика [-1.0 .. +1.0]
    speedProfile?: 'minimum_jerk' | 'linear' | 'ballistic';
    durationMs?: number;                    // Геймплейная длительность жеста
    qteWindowMs?: { min: number; max: number }; // Допустимый временной интервал для QTE
  };
}
```

### 8.3. Расширенный каталог 9 моторных примитивов L1

| Примитив | Назначение | Ключевые параметры | Примеры игровых сценариев |
| :--- | :--- | :--- | :--- |
| **`TAP`** | Одиночный клик / тап | `pos, holdMs=50, jitter=1.5px` | Кнопки UI, стрельба, выбор предметов в меню |
| **`DRAG`** | Плавное перетаскивание | `startPos, endPos, speedProfile, durationMs` | 2D-пазлы, инвентарь, перенос деталей в слот `M01` |
| **`SWIPE`** | Баллистический росчерк | `startPos, direction, velocity, durationMs` | Раннеры (смена полосы), броски гранат, перелистывание |

### 8.4. Внутренний цикл тикера L1 (16.6 мс на `hrtime`) и микро-джиттер
Внутри Node.js тикер работает на `process.hrtime.bigint()` с интервалом 16.6 мс:

```
Каждые 16.6 мс:
  ДЛЯ КАЖДОГО активного канала (pointerId 0..3):
    1. Если примитив = 'DRAG' или 'SWIPE' (в режиме Live Streaming):
       - Вычисляется tau = (now - startTime) / durationMs.
       - Flash-Hogan смещение: S(tau) = 10*tau^3 - 15*tau^4 + 6*tau^5.
       - Добавляется физиологический микро-тремор руки (Perlin Noise / Gaussian Jitter, sigma = 0.8px):
         P_final = P_base + Jitter(t).
       - send("press_move", { pointerId, x: P_final.x, y: P_final.y })
    2. Если примитив = 'HOLD_EVENT_CONDITIONED' (сбор ресурса / газ):
       - Проверяется условие: получено ли целевое событие (например OnResourceMined) или тайм-аут?
       - Если ДА:
           send("pointer_up", { pointerId, x, y })
           канал высвобождается.
       - Если НЕТ: палец удерживается на кнопке с субпиксельным дыханием руки.
    3. Если примитив = 'CONTINUOUS_STEER_STREAM' (стик машинки):
       - Обновляется вектор отклонения стика на основе физической траектории.
       - send("press_move", { pointerId, x: stickCenter.x + dx, y: stickCenter.y + dy })
    4. Физическая обратная связь (Closed-Loop Feedback):
       - Непрерывно проверяется эвристика сопротивления.
       - Если объект застрял — L1 прерывает движение и шлет в L2: RESISTANCE_DETECTED.
```

### 9.5.1. 1-секундный чек-ап легитимных задержек (1-Second Semantic Check-Up)
Каждые 1000 мс L2 делает семантический срез дерева состояний (MechanicStateSnapshot):
- Анимация сундука, катсцена, диалог NPC, воспроизведение нецикличной Spine/Animator анимации (isLooping == false,  locksInteraction == true) $\rightarrow$ **Легитимная игровая задержка (Legitimate In-Game Delay)**. Таймер подзадачи продлевается без ложных тревог.
- Анимаций нет (`isBusy == false`), окна открыты, хэш дерева состояний $\Delta \text{Tree}$ и дельта прогресса равны 0 более 3 секунд подряд $\rightarrow$ **Истинное застревание (Macro-Stagnation)** $\rightarrow$ смена тактики (Wiggle-раскачка, сброс предмета, откат сейва или вызов Micro-SLM).

#### 9.5.1.1. Пятислойный композитный чек-ап модальных окон и таймеров (5-Layer Composite Modal & Delay Policy)
Каждые 1000 мс L2 проводит комплексный многослойный анализ состояния экрана, исключая ложные срабатывания на рекламе, катсценах и отложенных крестиках:
1. **Слой 1: GDD-контракт (Design Rules):** Чтение требований из GDD (ожидаемая длительность рекламы, наличие скипа, таймер бесплатного спина рулетки). Если GDD декларирует показ видео 15 сек — L2 ожидает ровно заданный интервал.
2. **Слой 2: Контрактные маячки (`UrdtModalTarget`):** Проверка свойств `minDisplayDurationMs` и флага `isCloseAllowed`.
3. **Слой 3: Состояние компонентов сцены (Active Scene Engine State):** Проверка проигрывания видео (`UnityEngine.Video.VideoPlayer.isPlaying`), нециклических анимаций Spine/Animator (`locksInteraction == true`) и блокирующих частиц. Если сцена активно анимируется — таймер застоя замораживается.
4. **Слой 4: Сканирование текстовых паттернов таймера (Countdown Regex Scanner):** Модуль сканирует видимые строки TextMeshPro регулярным выражением `/\b(0?[0-9]|1[0-5])\s*(s|sec|сек)?\b/i`. Если число монотонно убывает (5..4..3..2..1) — фиксируется `LEGITIMATE_COUNTDOWN`, L2 пассивно ждет появления кнопки закрытия.
5. **Слой 5: Безусловный грейс-период (4.0s Grace Period & Fallback):** Любому новому модальному окну без крестика дается фиксированный грейс-период в 4.0 секунды перед объявлением тупика (`Soft-Lock`). Если по истечении 4 секунд ни таймер, ни анимация не обнаружены, а кнопки закрытия нет — окно объявляется `Soft-Lock Defect`.

### 9.5.2. Инструмент управляемой паузы мира при рассуждениях L3/L2 (`UrdtTimeScaleController`)
Во время глубоких когнитивных рассуждений L3 (3–10 секунд) или тяжелого инференса L2 агент может активировать управляемую паузу (`allowPauseOnDeliberation: true`), чтобы динамический мир не убегал вперед:
1. **Управление физическим временем:** Выставляется `Time.timeScale = 0.0f`, что останавливает физический цикл `FixedUpdate()` и `Update()`, привязанный к `Time.deltaTime`.
2. **Проблема не связанного с `Time.deltaTime` рантайма:**
   Многие игры содержат таймеры и подсистемы, работающие независимо от `Time.timeScale`. Для корректной паузы вводится протокол **`IUrdtPausable`**:
   - **`Time.unscaledDeltaTime` и `Time.realtimeSinceStartup`:** При включении паузы `UrdtTimeScaleController` фиксирует виртуальный оффсет времени `unscaledPauseOffset`. Игровые таймеры, использующие unscaled-время, считывают скорректированное значение через прокси `UrdtTime.UnscaledTime`.
   - **Анимации и твины (DOTween / LeanTween):** Твины, настроенные с `isTimeScaleIndependent: true`, принудительно ставятся на паузу через вызов `DOTween.PauseAll()` (или селективно по тегу `DOTween.Pause(UrdtTarget)`).
   - **Асинхронные таймеры (UniTask / Coroutines):** Для задержек реального времени (`UniTask.Delay(..., ignoreTimeScale: true)`) агент рассылает движковое событие `UrdtEvents.OnUrdtPauseStateChanged(isPaused: true)`. Компоненты, реализующие `IUrdtPausable`, приостанавливают свои внутренние тикеры.
   - **Аудио и видео:** Фоновые видеоролики (`VideoPlayer`) и звуковые эффекты при необходимости замораживаются.
3. **Изоляция транспорта URDT от игровой паузы:**
   Сетевые потоки URDT (WebSocket, Named Pipe, IPC), прием команд и сторожевые таймеры (Watchdog) работают в независимых системных потоках ОС на монотонных системных часах (`System.Diagnostics.Stopwatch` / `process.hrtime`). Это гарантирует, что даже при полной заморозке движка агент сохраняет 100% контроль над игрой, может считывать стейт и подавать команды разморозки.

### 8.8. Механизм инжекции синтетического ввода (Dual-Mode Input Injection)
Чтобы агент мог честно управлять любым проектом Unity без вмешательства в исходный код разработчиков, модуль `UrdtInputInjector.cs` поддерживает два режима инжекции:

1. **Режим New Input System (Unity 2020+, Основной стандарт):**
   - **Разрешение конфликта устройств:** Модуль проверяет наличие существующего тачскрина, чтобы не создавать паразитные дубликаты, ломающие `Touchscreen.current`:
     ```csharp
     var touchDevice = InputSystem.GetDevice<Touchscreen>() ?? InputSystem.AddDevice<Touchscreen>("UrdtVirtualTouchscreen");
     ```
   - **Индексация пальцев:** Сквозные синтетические каналы нумеруются со смещением `touchId = pointerId + 1` (диапазон `1..10`), что предотвращает конфликт с зарезервированным системой первичным индексом 0.
   - **Система координат:** Синтетические события позиционируются строго в **физических экранных пикселях (`Screen.width` / `Screen.height`)**. Для интерфейсов Canvas в режиме `Scale With Screen Size` (Reference Resolution) маячки конвертируют свои границы через `RectTransformUtility.WorldToScreenPoint(cam, worldCorners[i])`.
   - Команды L1 транслируются через низкоуровневый системный буфер событий:
     ```csharp
     InputSystem.QueueStateEvent(touchDevice, new TouchState {
         touchId = pointerId + 1,
         phase = currentPhase, // Began, Moved, Stationary, Ended
         position = physicalPixelPos,
         pressure = 1.0f
     });
     ```
   - **Преимущество:** Это активирует абсолютно все элементы управления в игре: события Action Maps, виртуальные экранные стики (`OnScreenStick`), мультитач-жесты `EnhancedTouch`, физические 3D/2D лучи и UGUI Canvas без каких-либо костылей.
2. **Режим Legacy / UGUI Fallback:**
   - Если в проекте выключен New Input System, инжектор переключается на дуальный мост:
     - **Для интерфейса (UGUI Canvas):** создание `PointerEventData` и прямая посылка через `ExecuteEvents.ExecuteHierarchy(target, pointerData, ExecuteEvents.pointerDownHandler)`.
     - **Для игрового мира (2D/3D сцены):** синтетический `Physics.Raycast` / `Physics2D.Raycast` с эмуляцией системных сообщений `OnMouseDown` / `IPointerClickHandler`.
     - **Для опроса Legacy Input (`Input.GetMouseButton`):** активация драйвера `UnityEngine.TestTools.Input` (или нативных Win32 SendInput в фокусе окна).
3. **Эмуляция удержания с троттлингом (`TouchPhase.Stationary`):**
   - Если палец удерживается на месте (примитив `HOLD_EVENT_CONDITIONED`), событие `TouchPhase.Stationary` троттлится до 10 Гц (раз в 100 мс), предотвращая переполнение системной очереди Event Queue Unity.
4. **Синхронизация с физическим шагом (FixedUpdate):**
   - Физические перемещения и манипуляции с телами Rigidbody диспатчатся строго в цикле `FixedUpdate()` (20 мс / 50 Гц) с согласованием `Time.fixedDeltaTime`, исключая эффект туннелирования и потерю коллизий.
5. **Диагностика невидимого перехвата клика (Raycast Hijacking & UI Overlay Detector):**
   - Перед посылкой любого клика или нажатия (`pointer_down`) L1 производит пре-опрос через `EventSystem.current.RaycastAll(pointerData, s_RaycastResultsPool)`.
   - Если верхний пораженный графический элемент в стеке (`s_RaycastResultsPool[0].gameObject`) не совпадает с целевым маячком и не является его родителем/потомком:
     - Синтетический ввод прерывается, и в L2 мгновенно рапортуется аппаратно точное событие:
       `BLOCKED_BY_UI_OVERLAY: { blocker: "TutorialDarkOverlay", raycastTarget: true, layer: "UI" }`.
     - Это позволяет мгновенно локализовать забытые прозрачные плашки, невидимые экраны загрузки и кривые туториальные маски без ложных обвинений игровой логики.
6. **Человеческая фиксация при отпускании детали в слот (Stationary Settle for Snap-to-Slot):**
   - При завершении примитива `DRAG` над гнездом слота L1 не бросает палец мгновенно, а активирует фазу естественной фиксации: палец удерживается в неподвижном состоянии (`TouchPhase.Stationary`) в течение $T_{\text{settle}} = 100\text{ мс}$ (5 физических тактов при 50 Гц).
   - За это время силы трения и физическое сопротивление движка естественным образом гасят линейную скорость $\vec{V} \to 0$, предотвращая случайный отскок (`Bounciness`) или пролет тела мимо слота по инерции. Лишь после этого посылается `pointer_up`.
7. **Внутридвижковый контрактный триггер для QTE (Sub-Frame Precision QTE Trigger):**
   - Для механик с экстремально узкими окнами реакции (QTE, ритм-игры, парирование с таймингом 50–100 мс) посылка команды через сетевой сокет (IPC/WebSocket) с задержкой 1–5 мс создает риск запаздывания.
   - L2 передает в инжектор декларативный контракт предикатного клика:
     `SCHEDULE_PREDICATE_TAP: { targetId: "indicator_arrow", condition: "normalizedPos >= 0.85 && normalizedPos <= 0.95", timeoutMs: 2000 }`.
   - C#-компонент `UrdtInputInjector.cs` оценивает предикат на каждом кадре внутри `Update()` / `FixedUpdate()`, и в момент выполнения условия мгновенно инжектирует `pointer_down` на субкадровом уровне с нулевой сетевой задержкой ($\Delta t = 0\text{ мс}$).
   - Факт срабатывания асинхронно логируется в L2: `QTE_TRIGGERED_IN_ENGINE: { frame: Time.frameCount, errorMarginMs: 0.12 }`.
8. **Взаимодействие с плавающими виртуальными стиками (Floating Dynamic Joysticks):**
   - Для мобильных экшенов и шутеров, где виртуальный стик не зафиксирован на экране, а появляется в точке первого касания, компонент `UrdtUiStickTarget.cs` поддерживает контракт `isFloating: true` с зоной активации `activationAreaRect` (например, левая половина экрана).
   - При исполнении примитива `CONTINUOUS_STEER_STREAM`:
     1. L1 выполняет первичное касание `TouchPhase.Began` в геометрическом центре допустимой зоны ($P_{\text{anchor}} = \text{center}(\text{activationAreaRect})$), фиксируя точку динамического якоря стика.
     2. Последующие фазы `TouchPhase.Moved` транслируют вектор отклонения $\vec{v} \in [-1.0 .. +1.0]$ как смещение пальца $P_{\text{finger}} = P_{\text{anchor}} + \vec{v} \cdot R_{\text{stick}}$, где $R_{\text{stick}}$ — радиус хода стика.
     3. При завершении руления L1 отправляет `TouchPhase.Ended`, высвобождая стик и возвращая персонажа в нейтральное состояние.

### 8.9. Инженерные тонкости интеграции Spine 2D и Mecanim Animator
Для исключения ошибок рассинхронизации анимаций и перегрузки памяти внедрены специализированные адаптеры:

1. **Dual-Spine Bridge (`SkeletonAnimation` vs `SkeletonGraphic`):**
   - Раздельный сэмплинг жизненного цикла: `SkeletonAnimation` (2D-персонажи мира) инспектируется в `LateUpdate()`, а `SkeletonGraphic` (UI Canvas) — внутри `CanvasUpdateRegistry`.
   - **Отслеживание Mix/Crossfade:** При плавном переходе между анимациями (`TrackEntry.MixDuration > 0`), когда событие `OnComplete` может не сработать из-за досрочного перебивания новым клипом, адаптер запускает независимый таймер прогресса трека `trackTime >= animation.duration`.
   - **Пул событий Spine (Zero-Alloc):** Параметры `EventData` из кастомных событий Spine (`spine_user_event`) копируются в предвыделенный пул структур без создания объектов в куче.
2. **Deep Mecanim Scanner (Суб-машины и деревья смешивания):**
   - **Вложенные Sub-State Machines:** Вместо вызова `stateInfo.IsName()`, возвращающего только имя корня, маячок считывает полный хэш пути состояния через `Animator.GetCurrentAnimatorStateInfo(layer)`.
   - **Blend Trees:** Для состояний смешивания отслеживается не имя клипа, а активные float-параметры весов смешивания (например, `MoveSpeed`, `TurnAngle`).
   - **Квантование зацикленных анимаций:** Для `isLooping == true` значение нормализованного времени приводится к диапазону $[0.0 .. 1.0)$ через `normalizedTime % 1.0f`.

## 9. ДЕТАЛЬНАЯ АРХИТЕКТУРА УРОВНЯ L2: Тактический диспетчер и когнитивный арбитр

### 9.1. Назначение и место в системе
Уровень **L2** — «мозжечок и тактическая память». Он принимает глобальную задачу от L3 (например: *«Пройти механику M01: Snap to Slot»* или *«Завершить круг заезда»*), ведет агента через цепочки окон и состояний, отслеживает динамические опасности мира и вовремя переключает режимы.

### 9.2. Структура состояния тактического графа (`L2TacticalState`)
```typescript
interface L2TacticalState {
  currentMissionGoal: string;             // Глобальная цель от L3 ("Завершить заезд на 3 круга")
  activeSubGoal: string;                  // Подзадача ("Удерживать газ и вписаться в поворот #2")
  
  activeTouchChannels: Map<number, {

    hazardId: string;

  activeModalWindow: string | null;       // "SpecialOfferModal", "RateUsDialog", null

  expectedTransitions: Map<string, string>;// Известный граф переходов интерфейса
```

   - Есть деталь `item_square` с `isSnapped == false` и `isJunk == false`.

### 9.4. Двухуровневый тактический контур (HTN-over-BT Hybrid Executive)
Вместо изолированного использования HTN или деревьев поведения, в L2 реализован **двухуровневый гибридный исполнитель**:

```
 ┌───────────────────────────────────────────────────────────────────────────┐
 │               ВЕРХНИЙ УРОВЕНЬ: HTN PLAN GENERATOR (Макро-план)            │
 │   Формирует осмысленный иерархический план подзадач из GDD и маячков:     │
 │   [NavigateToShop] ──► [SelectTab:Weapons] ──► [TapItem:Sword] ──► [Buy] │
 └─────────────────────────────────────┬─────────────────────────────────────┘
                                       │ Текущий шаг плана (SubGoal)
                                       ▼
 ┌───────────────────────────────────────────────────────────────────────────┐
 │             НИЖНИЙ УРОВЕНЬ: REACTION BEHAVIOR TREE (Тик каждые 50 мс)     │
 │   Селектор приоритетов исполнения:                                        │
 │   ├─ Приоритет 1 (Critical): Детект угрозы/урона ──► Уклонение / Блок    │
 │   ├─ Приоритет 2 (Interrupt): Модальное окно ──► Закрытие / Ответ         │
 │   └─ Приоритет 3 (Default): Исполнение текущего шага HTN через примитив L1│
 └─────────────────────────────────────┬─────────────────────────────────────┘
                                       │ При сбое шага / блокировке
                                       ▼
                       [ ОБРАТНАЯ СВЯЗЬ: REPLAN_REQUIRED ]
                 (HTN мгновенно перестраивает план в обход сбоя)
```

1. **Верхний тактический уровень (HTN Plan Generator):**
   - Использует стандартизированный JSON-DSL. Если в GDD нет жесткого скрипта, HTN автоматически генерирует доступные операторы (`TapTarget`, `DragTo`, `WaitEvent`, `ContinuousSteer`) на основе списка активных маячков сцены.
2. **Исполнительный реактивный уровень (Behavior Tree Executor):**
   - Тикает каждые 50 мс. Проверяет предусловия текущего шага HTN.
   - Если путь свободен — транслирует моторный примитив в L1.
   - Если во время движения персонажа атаковал противник или появилось диалоговое окно — BT немедленно перехватывает управление, выполняет реактивное действие (уклонение или закрытие окна), а затем возвращается к HTN-плану.
3. **Обратная связь и защита от бесконечных галлюцинаций (BT-to-HTN Re-Plan & Loop-Break):**
   - Если целевой элемент уничтожен, кнопка заблокирована или BT фиксирует непреодолимый застой — BT генерирует сигнал `REPLAN_REQUIRED` с контекстом сбоя, инициируя перепланирование оставшейся цепочки HTN.
   - **Топологический инвариант отсечки (Loop-Break Invariant):** HTN-планировщик ведет историю состояний графа в текущей сессии $\mathcal{P} = [V_0, V_1, \dots]$. Если сгенерированный альтернативный план возвращает агента в ранее пройденный узел графа $V_k \in \mathcal{P}$ без изменения прогресса игры ($\Delta \text{Progress} = 0$), этот путь признается тупиковой веткой (`ExhaustedBranch`).
   - Если **2 альтернативных плана подряд замкнулись в кольцо**, либо суммарное число попыток репланирования одной подцели превысило **3 попытки** — планировщик немедленно останавливает перебор и генерирует `Failure Evidence Packet` с категорией дефекта `DEADLOCK_TOPOLOGY`.

### 9.5. Динамический семантический чек-ап (`UrdtStagnationPolicy`) и поведение при задержках SLM
1. **Динамическая рантайм-политика детекции застоя (`UrdtStagnationPolicy`):**
   - Понятие «зависания/застоя» не хардкодится одной константой, а настраивается **слоем L2 в рантайме под контекст игры**:
     - *Раннер / Аркада:* Застой фиксируется, если `velocity < 0.1` м/с в течение 0.5 секунды.
     - *Головоломка / Match-3:* Неподвижность до 15 секунд считается нормальным процессом решения, застой фиксируется только по отсутствию прогресса и доступных ходов.
     - *UI и диалоги:* Застой фиксируется строго по отсутствию смены состояния экрана при активных попытках кликов.
   - **Фильтрация непрерывного шума:** При вычислении хэша состояния ($\Delta \text{Tree}$) непрерывные микро-колебания idle-анимаций (покачивание меша на 0.001 м) и системы частиц маскируются и исключаются из сравнения.
2. **Поведение L1 во время инференса Micro-SLM (40–150 мс):**
   - В момент отправки запроса в SLM слой L2 задаёт политику поведения быстрого контура (`on_deliberation_policy`):
     - `SAFE_COAST`: L1 плавно доводит текущий начатый жест до конца и переходит в безопасное удержание, исключая неконтролируемый занос персонажа.
     - `SAFE_HOLD`: Удержание текущей позиции виртуального стика или кнопки.
     - `SAFE_RELEASE`: Немедленное снятие пальцев во избежание случайных нажатий.
     - `PAUSE_TIMESCALE`: Кратковременная установка `Time.timeScale = 0` (только в QA-сборках при необходимости абсолютного детерминизма).
     - `ASYNC_BUFFERING`: Агент удерживает безопасную нейтраль.
     - **Категорический запрет `Time.timeScale = 0` в Headless CI:** В автономном режиме заморозка времени блокирует `FixedUpdate`, что приводит к эффекту телепортации и проваливанию коллайдеров при резком залповом применении накопившихся команд после разморозки.
3. **Защита от утечек памяти в истории действий:**
   - Поле `recentActionHistory` реализуется строго как циклический буфер фиксированного размера (на 50 последних шагов), предотвращая раздувание Node.js Heap при многочасовых CI-прогонах.
4. **Стратегия деградации при отсутствии Micro-SLM:**
   - Если модель `qwen2.5-1.5b` временно недоступна, L2 автоматически переходит на детерминированный эвристический алгоритм (Deterministic Rule-Based Navigation) с приоритетным обходом кнопок закрытия (`btn_close`, `Cancel`, `Back`), не прерывая выполнение тестового контура.

### 9.5.1. 1-секундный чек-ап легитимных задержек (1-Second Semantic Check-Up)
Каждые 1000 мс L2 делает семантический срез дерева состояний (MechanicStateSnapshot):
- Анимация сундука, катсцена, диалог NPC, воспроизведение нецикличной Spine/Animator анимации (isLooping == false, locksInteraction == true) $\rightarrow$ **Легитимная игровая задержка (Legitimate In-Game Delay)**. Таймер подзадачи продлевается без ложных тревог.
- Анимаций нет (`isBusy == false`), окна открыты, хэш дерева состояний $\Delta \text{Tree}$ и дельта прогресса равны 0 более 3 секунд подряд $\rightarrow$ **Истинное застревание (Macro-Stagnation)** $\rightarrow$ смена тактики (Wiggle-раскачка, сброс предмета, откат сейва или вызов Micro-SLM).

#### 9.5.1.1. Пятислойный композитный чек-ап модальных окон и таймеров (5-Layer Composite Modal & Delay Policy)
Каждые 1000 мс L2 проводит комплексный многослойный анализ состояния экрана, исключая ложные срабатывания на рекламе, катсценах и отложенных крестиках:
1. **Слой 1: GDD-контракт (Design Rules):** Чтение требований из GDD (ожидаемая длительность рекламы, наличие скипа, таймер бесплатного спина рулетки). Если GDD декларирует показ видео 15 сек — L2 ожидает ровно заданный интервал.
2. **Слой 2: Контрактные маячки (`UrdtModalTarget`):** Проверка свойств `minDisplayDurationMs` и флага `isCloseAllowed`.
3. **Слой 3: Состояние компонентов сцены (Active Scene Engine State):** Проверка проигрывания видео (`UnityEngine.Video.VideoPlayer.isPlaying`), нециклических анимаций Spine/Animator (`locksInteraction == true`) и блокирующих частиц. Если сцена активно анимируется — таймер застоя замораживается.
4. **Слой 4: Сканирование текстовых паттернов таймера (Countdown Regex Scanner):** Модуль сканирует видимые строки TextMeshPro регулярным выражением `/\b(0?[0-9]|1[0-5])\s*(s|sec|сек)?\b/i`. Если число монотонно убывает (5..4..3..2..1) — фиксируется `LEGITIMATE_COUNTDOWN`, L2 пассивно ждет появления кнопки закрытия.
5. **Слой 5: Безусловный грейс-период (4.0s Grace Period & Fallback):** Любому новому модальному окну без крестика дается фиксированный грейс-период в 4.0 секунды перед объявлением тупика (`Soft-Lock`). Если по истечении 4 секунд ни таймер, ни анимация не обнаружены, а кнопки закрытия нет — окно объявляется `Soft-Lock Defect`.

### 9.6. Адаптивный навигационный селектор под игру (Adaptive Navigation Selector)
1. **По цепочке вейпоинтов (`UrdtWaypointTarget`):** В гонках и на сплайнах (`M08_WaypointTracking`).
2. **Метод потенциальных полей (Artificial Potential Fields):** В динамических играх — цель притягивает, метеориты и стены отталкивают.
3. **Прямой вектор с лучевым обходом:** В 2D/3D экшенах на арене.
4. **Дискретный селектор полос:** В раннерах (`M13_LaneSwitcherRunner`).

### 9.7. Когнитивный арбитр Micro-SLM (Qwen2.5-1.5B via `node-llama-cpp`)
Модель `qwen2.5-1.5b-instruct-q4_k_m.gguf` загружается в оперативную память при старте агента (занимает ~1.1 ГБ RAM, инференс на CPU занимает 40–60 мс):
- **Принцип абсолютного паритета окружений:** Модель Micro-SLM **строго обязательна к исполнению во всех окружениях** — как в интерактивном режиме Unity Editor, так и в автоматических CI/CD раннерах. Любое отключение или замена нейросетевого арбитра на упрощенные правила в CI категорически запрещены, что гарантирует 100% повторяемость тестов и исключает расхождения между локальным прогоном и ночным пайплайном. Минимальные системные требования для CI-раннера: 2 vCPU, 2 ГБ выделенной памяти под процесс CoreAgent.

```text

ЦЕЛЬ: "Поместить синий куб в слот"
ТЕКУЩИЙ ЭКРАН:
- Активное окно: "SpecialOfferModal" (Блокирует экран: true)

Выдай строго JSON:
```

### 9.8. Трехэшелонная защита от галлюцинаций Micro-SLM
1. **Эшелон 1 (GBNF-фильтр в `node-llama-cpp`):** Грамматика физически блокирует токены вне списка текущих ID кнопок.
2. **Эшелон 2 (Пост-валидация Zod):** При повреждении JSON — 1 мгновенный ретрай с сообщением об ошибке схемы.
3. **Эшелон 3 (Детерминированный фоллбек):** При повторном сбое — безопасный клик по крестику закрытия (`btn_close`) или эскалация в L3.

### 9.9. Трехступенчатая защита от зацикливания (Anti-Looping)
1. **Хэширование State-Action (Ring Buffer):** Пара $(S, A)$, повторенная 2 раза без дельты, блокируется как `INEFFECTIVE`.
2. **Запрет в промпте Micro-SLM:** Список заблокированных кнопок передается в `forbidden_targets`.
3. **Exploration Jitter:** Микро-свайп раскачки (Wiggle) или нейтральный клик для выхода из тупика.

### 9.10. Механизм эскалации сбоев на Уровень L3 и замкнутый цикл авто-починки (Closed-Loop Self-Healing)
Если L2 перепробовал 3 попытки, но `stuckCounter >= 3` и физическое состояние не прогрессирует:
- L2 не падает в бесконечный цикл.
- Формирует **Пакет доказательств сбоя (Failure Evidence Packet)**:
  - Снапшот маячков в момент сбоя (координаты, скорости, флаги).
  - Список последних выполненных примитивов ввода.
  - Лог активных коллизий и падения скоростей.
  - Идентификатор нарушенного правила GDD.
- **Двойной целевой экспорт (Dual Export Protocol):**
  1. **Для ИИ-кодера (Machine Loop):** Пакет немедленно сохраняется в стандартизированный файл `.harness/failure_evidence.json` в корне репозитория. Это позволяет CLI-агентам (OpenAI Codex / Google Antigravity / Harness Protocol `cli-judge.js`) мгновенно считать контекст бага, обнаружить сбойный C# скрипт в Unity и автоматически сгенерировать коммит с исправлением логики механики.
  2. **Для человека-разработчика (Human Loop):** Пакет встраивается в интерактивный дашборд `Docs/QA_Audit_Report.html` с интерактивной временной шкалой, трассировкой маячков и рекомендациями по исправлению.
- Передает пакет наверх в **L3 (Стратег)**:
  *«Механика M01 заблокирована: деталь item_square застревает на координатах (450, 310). Фиксирую дефект физики»*.

### 9.11. Комбинированный интерфейс связи L2 с L3
1. **Быстрый телеметрический канал (Fast Telemetry Stream):** Легковесный JSON-прогресс (`progress`, `activeStep`, `timeElapsed`) в живой дашборд оператора без вызова LLM.
2. **Когнитивное пробуждение L3 (Event-Driven Awakening) и синхронизация паузы:**
   - Граф LangGraph просыпается только при событиях `PHASE_COMPLETED` или `PHASE_FAILED_DEFECT`.
   - В момент когнитивного пробуждения L3 для анализа глубокого сбоя или планирования гипотез L2 может опционально запросить управляемую паузу игрового мира (через команду `urdt_pause_world`), предотвращая расползание состояния динамической сцены во время многосекундных рассуждений LLM.

### 9.12. Естественный цикл Game Over и рестарта
При гибели (`OnPlayerDied`): поиск в UI кнопок `Retry`, `Restart`, `Again`, клик через `TAP`, проверка сброса состояния и возобновление прогона.

## 10. ДЕТАЛЬНАЯ АРХИТЕКТУРА УРОВНЯ L3: Стратег-Ревьюер и Многослойная Топологическая Карта (Runtime Graphify)

### 10.1. Трехуровневая модель GDD-комплаенса и дуальная резолюция источников (Dual-Source Resolution)
L3 парсит спецификацию механик по приоритетной дуальной схеме:
1. **Приоритет 1 (Локальный оверрайд проекта):** Поиск локального markdown-документа по пути `Docs/Specs/{MechanicId}.md` (или `Docs/GDD/*.md`). Если проект содержит локальные спецификации, они берутся за абсолютную основу требований, обеспечивая автономность репозитория.
2. **Приоритет 2 (Глобальная База Знаний KBPro):** Если локальный файл отсутствует, модуль `gdd_parser_bridge.ts` обращается к центральной Базе Знаний (`KBPRO_AI_CHAT_WIKI_DIR`, например `E:\KBProData\knowledge-base`) через `KBProGDDParser`.

Извлеченные требования структурируются в 3 слоя правил:
1. **Макро-уровень (DoD Чек-лист):** Перечень глав и требований готовности (например, *«Раздел 4: Гонки на время — 3 круга»*).
2. **Мезо-уровень (Контрактные инварианты):**
   - Формула: `Precondition -> Action -> Expected Invariant`.
   - Примеры:
     - `INV-01 (Happy Path)`: Помещение правильной детали в слот $\rightarrow$ `isOccupied == true` и `progress += 1`.
     - `INV-02 (Negative/Exploit)`: Помещение бракованной детали `isJunk == true` $\rightarrow$ слот отталкивает деталь, `isOccupied == false`.
3. **Микро-уровень (Оперативные гипотезы на лету):** Динамическая генерация проверяемых гипотез перед входом в конкретную механику.

### 10.2. Архитектура графа LangGraph (Узлы пайплайна)
Уровень L3 строится на `@langchain/langgraph` с переиспользованием наработок `E:\Projects\HarnessProtocol`:
1. **Узел `IngestGDDNode`:** Читает дизайн-документ механики из базы знаний `E:\KBProData\knowledge-base` или локальной папки `Docs/`.
2. **Узел `DecomposeRulesNode`:** Извлекает формальные контрактные инварианты (`INV-01`, `INV-02`).
3. **Узел `ExperimentPlannerNode`:** Формирует матрицу испытаний для L2 (штатное прохождение vs намеренная попытка сломать механику).
4. **Узел `RuntimeGraphifyNode`:** Агрегирует топологический мультиграф игры по мере её прохождения.
5. **Узел `AuditReportNode`:** После прогона всех механик генерирует итоговые отчеты (`Docs/QA_Audit_Report.html` и Markdown-выгрузку).

### 10.3. Архитектура Runtime Graphify: Многослойная Топологическая Карта Приложения
В процессе исследования агент строит ориентированный мультиграф игры $\mathcal{G} = (V, E)$, где:
- **Узлы ($V$):** Семантические состояния игры (состояние окон, экранов, сцен).
- **Ребра ($E$):** Доступные аффордансы/действия (клик по кнопке, свайп, завершение диалога, сбор ресурса).

```
                     МНОГОСЛОЙНАЯ ТОПОЛОГИЧЕСКАЯ КАРТА (4 СЛОЯ)
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ СЛОЙ 1: UI Navigation Graph (Экраны, Меню, Всплывающие Окна, Диалоги)       │
 │ [MainMenu] ──(click:btn_play)──► [SelectLevel] ──(click:lvl_01)──► [GameUI] │
 ├─────────────────────────────────────────────────────────────────────────────┤
 │ СЛОЙ 2: Data & Progression Graph (Экономика, Очки, Инвентарь, Валюта)       │
 │ {Score: 0, Ore: 0} ──(mine_node)──► {Score: 100, Ore: 5, LevelUnlocked: 2} │
 ├─────────────────────────────────────────────────────────────────────────────┤
 │ СЛОЙ 3: Spatial World Graph (2D/3D Пространство, Комнаты, Арены, Зоны)     │
 │ [SpawnPoint] ──(navigate:corridor_A)──► [BossArena] ──(exit)──► [SafeZone]   │
 ├─────────────────────────────────────────────────────────────────────────────┤
 │ СЛОЙ 4: Element Affordance Graph (Маячки и допустимые действия в текущий миг)│
 │ [Urdt2DDraggable] ──(can_drag_to)──► [Urdt2DSlot] (Status: IsOccupied=false)│
 └─────────────────────────────────────────────────────────────────────────────┘
```

### 10.4. Двойная ценность топологической карты:
1. **Инструментарий навигации агента:** Агент использует карту для поиска пути (A* / BFS по графу игры): *«Чтобы протестировать механику M14, нужно пройти: MainMenu $\rightarrow$ LevelSelect $\rightarrow$ Page2 $\rightarrow$ Button_M14»*.
2. **Мгновенная диагностика дефектов структуры игры:**
   - **Тупики (Deadlock Nodes):** Состояния, из которых нет исходящих ребер (отсутствует кнопка закрытия или «Назад»).
   - **Недостижимые состояния (Orphan / Unreachable Screens):** Окна и префабы, к которым невозможно проложить путь из начальной точки.
   - **Сломанные ребра (Broken Transitions):** Кнопка нажимается, но состояние графа не меняется (неработающий интерфейс).
   - **Бесконечные ловушки (Infinite Loops):** Циклы диалогов или окон, из которых нельзя выйти в геймплей.
   - **Сетевые зависания и потеря связи (Network Disconnect & Reconnection UX Defects):** При потере сетевого соединения агент проверяет контракт пользовательского опыта как живой игрок: обязательное появление модального окна переподключения (`RECONNECTING_DIALOG`) за время $\le 3$ с, наличие интерактивной кнопки повтора (`RETRY`) и возможность корректного выхода в главное меню без мертвого зависания экрана (Silent UI Freeze).

### 10.5. Автономный интерактивный HTML-дашборд (`QA_Audit_Report.html`)
Отчет генерируется в виде **полностью автономного (Self-Contained) HTML-файла**, не требующего интернета:
1. **Интерактивный граф Runtime Graphify:** Встроенная визуализация топологической карты игры (Canvas/SVG), где разработчик может кликать по узлам, а проблемные тупики и баги подсвечены **КРАСНЫМ**.
2. **Временная шкала прогона (Interactive Timeline):** Посекундный лог действий агента, событий движка и зафиксированных угроз.
3. **Карточки багов (GDD Discrepancy Cards):**
   - Пункт GDD, который был нарушен.
   - Слой топологии, где возник дефект (UI / Data / Spatial / Physics).
   - Шаги воспроизведения (Repro Steps) со снапшотом маячков в момент сбоя.
4. **Дорожная карта видеофиксации:** Спецификация для встраивания 5-секундных видеороликов момента бага напротив временной отметки.
5. **Встроенный аварийный видеорегистратор (In-Memory Crash Dashcam):**
   - Вместо непрерывной тяжелой записи видео (которая просаживает FPS и забивает диск сотнями мегабайт в CI), C#-модуль `UrdtCrashDashcam.cs` непрерывно пишет в кольцевой буфер оперативной памяти (Ring-Buffer) 25 легковесных кадров с разрешением 640x360 в формате JPEG (качество 60%, ~60 КБ на кадр).
   - Частота сэмплирования: 5 кадров в секунду ($T = 200\text{ мс}$), что обеспечивает скользящее 5-секундное окно истории происходящего.
   - Суммарный объем буфера в RAM составляет всего **~1.5 МБ**, что абсолютно безопасно для памяти. Кадры читаются через `AsyncGPUReadback`, исключая микрофризы основного потока рендеринга.
   - При наступлении сбоя (краш, тупик, нарушение GDD-инварианта) буфер замораживается, сшивается встроенным энкодером в компактный анимированный WebP/GIF и встраивается как `data:image/webp;base64,...` непосредственно в карточку дефекта отчета `QA_Audit_Report.html` и пакет доказательств `UrdtFailureEvidencePacket`.

### 10.6. Спецификация структур данных топологического мультиграфа ($V$ и $E$)

Для математически строгого построения графа $\mathcal{G} = (V, E)$ определены следующие типы данных:

1. **Структура вершины (Semantic State Node $V$):**
```typescript
interface UrdtGraphNode {
  nodeId: string;              // 64-битный хэш MurmurHash3 от нормализованного дискретного состояния
  screenType: 'MAIN_MENU' | 'LEVEL_SELECT' | 'GAMEPLAY_ARENA' | 'MODAL_DIALOG' | 'INVENTORY' | 'VICTORY' | 'DEFEAT';
  sceneName: string;           // Имя активной Unity сцены
  activeModalId: string | null;// Имя блокирующего окна (если есть)
  
  // Дискретные семантические инварианты (с защитой от комбинаторного взрыва состояний!):
  stateDescriptor: {
    interactiveBeaconIds: string[]; // Отсортированный алфавитно массив активных ID маячков
    progressionPhase: string;       // "TUTORIAL_STEP_1", "WAVE_3", "BOSS_FIGHT"
    questFlagsHash: number;         // Битовая маска ключевых дискретных флагов игры
    normalizedTexts: string[];      // Тексты UI с заменой динамических чисел (\d+) на маркер <NUM>
  };
  
  firstDiscoveredTimestamp: number;
  visitCount: number;
  isTerminal: boolean;         // Экран завершения игры / Победа / Поражение
}
```

#### 10.6.1. Защита топологического графа от взрыва состояний (State Explosion Protection)
Чтобы граф не разрастался до десятков тысяч паразитных узлов из-за меняющихся счетчиков таймеров, золота или динамических анимаций, функция хэширования `computeNodeHash(state)` применяет жесткую нормализацию:
1. **Маскирование динамических чисел (Regex Digit Masking):** Все числа в строковых лейблах кнопок и текстовых полях TextMeshPro заменяются регулярным выражением `/\b\d+([.,]\d+)?\b/g` на токен `<NUM>`. Значения *"Золото: 154"* и *"Золото: 210"* схлопываются в один семантический инвариант `Золото: <NUM>`.
2. **Алфавитная сортировка маячков:** Массив `interactiveBeaconIds` принудительно сортируется (`ids.sort()`), исключая зависимость хэша от случайного порядка итерации `GetComponentsInChildren`.
3. **Отсечение элементов вне зоны видимости (ScrollRect Culling):** Элементы интерфейса внутри списков прокрутки (`ScrollRect`), выходящие за пределы маски вьюпорта (`!viewportRect.Contains(elementScreenPos)`), исключаются из дескриптора узла, пока не будут проскроллены в зону видимости.
4. **Фильтрация непрерывных координат:** Физические float-координаты персонажа и объектов мира полностью исключены из хэша $V$. В узел включается только пространственная зона (сектор/комната), если на ней висит маркер зоны `UrdtSpatialZone`.
5. **Композитный скоуп сцен (Composite Multi-Scene Scope):** При аддитивной загрузке нескольких сцен одновременно (`LoadSceneMode.Additive` или Addressables) маячки агрегируются со всех активных сцен. Идентификатор сцены `sceneName` в вершине $V$ формируется как композитная строка: `MainGameplayScene + [HUDOverlay, PauseDialog]`, где аддитивные сцены отсортированы по алфавиту. Это предотвращает создание разрозненных графов для оверлейных интерфейсов.
6. **Жанрово-адаптивная семантическая свертка процедурных миров (Genre-Adaptive Procedural Quantization):**
   Для предотвращения комбинаторного взрыва состояний в процедурно генерируемых играх движок Runtime Graphify применяет контекстные адаптеры квантования:
   - **Match-3 и блочные головоломки:** Координаты фишек и суррогатные ID клонов (`gem_red_4182(Clone)`) полностью исключены из хэша вершины $V$. Дескриптор узла кодирует только цель уровня (`Target: Apples, Remaining: <NUM>`), флаг допустимых ходов (`hasValidMoves: boolean`) и статус фазы (`GAMEPLAY_MATCH3`). Все ходы свопа отображаются компактными ребрами-петлями внутри одного узла `[Match3_ActiveBoard]`, предотвращая раздувание графа до астрономических $6^{64}$ узлов.
   - **Бесконечные раннеры (Endless Runners):** Непрерывно возрастающая координата $Z$ и процедурные префабы дорожных препятствий отсекаются от графа и транслируются в L2 строго как динамические угрозы (`detectedHazards`). Вершина $V$ фиксирует дискретный конечный автомат полос (**Lane-State**: `LANE_LEFT` | `LANE_CENTER` | `LANE_RIGHT`, `RUNNING` | `JUMPING` | `SLIDING`) и макро-зоны биомов (вокзал, туннель, мост), сворачивая многокилометровый забег в чистую матрицу перестроений.
   - **Рогалики и процедурные подземелья (Roguelike Dungeons):** Узлы графа генерируются строго на границах комнат при пересечении дверей или порталов. Вершина идентифицируется по мета-архетипу (`RoomArchetype: START | COMBAT | SHOP | TREASURE | BOSS`) и статусу зачистки (`RoomStatus: IN_COMBAT` $\to$ `ROOM_CLEARED`). Динамический бой внутри комнаты не плодит паразитные вершины, а отражается как локальное тактическое состояние.

2. **Структура ребра (Affordance Transition Edge $E$):**
```typescript
interface UrdtGraphEdge {
  edgeId: string;
  fromNodeId: string;
  toNodeId: string;
  actionPrimitive: 'TAP' | 'DRAG' | 'SWIPE' | 'CONTINUOUS_STEER' | 'TIMEOUT_WAIT';
  targetBeaconId: string;
  
  kinematicParams: {
    screenNormalizedStart: [number, number];
    screenNormalizedEnd?: [number, number];
    durationMs: number;
  };
  
  transitionLatencyMs: number; // Время между завершением ввода и сменой узла
  traversalCount: number;      // Сколько раз переход успешно сработал
  successRate: number;         // Доля успешных переходов (0.0 .. 1.0)
}
```

### 10.7. Четырехуровневый алгоритм детекции дефектов (Frontier Exhaustion + GDD Compliance + Visual Layout + Async Asset Streaming)
Классификация тупиков и багов разделяется на три независимых уровня верификации:

1. **Уровень 1: Эвристика исчерпания фронтира (Frontier Exhaustion & Engine Health):**
   - Узел помещается в очередь исследования (`Frontier Queue`), пока на нём есть непроверенные интерактивные элементы.
   - **Фиксированная глубина вариации ($K = 3$):** Каждый доступный маячок на экране опрашивается ровно $K = 3$ раза с микро-вариацией параметров (клик по центру, клик с небольшим смещением на 5px, клик с удлинённым удержанием на 80 мс).
   - Если все доступные маячки на экране опробованы агентом $K$ раз, но состояние экрана не изменилось, на экране отсутствует кнопка «Назад / Закрыть», и таймер бездействия (5000 мс) истёк $\rightarrow$ узел объявляется **Критическим дефектом тупика (Soft-Lock Defect)**.
   - Если при попытке перехода в консоли движка зафиксирован `NullReferenceException`, рассинхронизация EventSystem или зависание Spine-анимации на незацикленном кадре $\rightarrow$ фиксируется **Функциональный краш (Crash Defect)**.
   - Если процесс движка внезапно погибает с нативным сигналом OS (`SIGSEGV`, `0xC0000005`, `SIGKILL`/OOM) $\rightarrow$ сторожевой процесс Post-Mortem Crash Watchdog считывает нативный стектрейс из `Player.log` и регистрирует **Фатальный нативный краш (`NATIVE_ENGINE_CRASH`)**.
2. **Уровень 2: Строгая верификация воронки GDD (GDD Compliance Violation):**
   - Построенный граф сверяется с матрицей переходов из дизайн-документа:
     - Если экран в GDD заявлен как обязательный промежуточный узел онбординга, но агент не может пройти дальше $\rightarrow$ фиксируется дефект блокировки прогресса.
     - Если переход ведёт на непредусмотренный экран (например, кнопка «Магазин» открывает экран настроек) $\rightarrow$ фиксируется дефект расхождения маршрутизации интерфейса.
3. **Уровень 3: Аппаратный аудит верстки и локализации (`UrdtLayoutInspector`):**
   - Автоматический скрининг всех активных компонентов `TextMeshProUGUI` и их контейнеров `RectTransform` при каждом открытии окна или смене языка:
     - **Обрезка текста (Text Truncation):** Считывание свойств `tmp.isTextOverflowing` и `tmp.isTextTruncated`. Если текст обрезан с многоточием или скрыт маской без возможности скролла $\rightarrow$ фиксируется дефект `LAYOUT_TEXT_TRUNCATED`.
     - **Геометрическое выпадение (Bounds Overflow):** Сопоставление экранных углов `RectTransform` текста с границами родительской кнопки. Наезд текста на соседние элементы цены или иконки $\rightarrow$ дефект `LAYOUT_BOUNDS_OVERFLOW`.
     - **Критическое уменьшение кегля (Auto-Size Degeneration):** Если `enableAutoSizing == true` и текущий размер `fontSize < 10.0f` (нечитаемый микро-текст) $\rightarrow$ дефект `LAYOUT_FONT_DEGRADATION`.
     - **Потерянные глифы (Missing Glyphs):** Детекция неразрешенных символов шрифтового атласа в `tmp.textInfo.characterInfo` (подстановка глифа `\uFFFD` или квадрата) $\rightarrow$ дефект `LAYOUT_MISSING_GLYPHS`.
   - Дефекты верстки привязываются к узлу топологического графа и отображаются в отчете `QA_Audit_Report.html` в секции «Дефекты локализации и интерфейса» с карточкой элемента.
4. **Уровень 4: Мониторинг асинхронной загрузки ассетов и CDN (`UrdtAsyncLoadingInspector`):**
   - **Проблема ложных софт-локов:** При переходе между локациями, загрузке глав или открытии витрины магазина игра инициирует фоновую загрузку бандлов через Addressables (`DownloadDependenciesAsync`) или `UnityWebRequest`. Во время загрузки UI блокируется оверлеем (`CanvasGroup.blocksRaycasts = true`), а прогресс-бар медленно заполняется по сети. Стандартный 5-секундный таймер бездействия ошибочно признал бы игру сломанной.
   - **Гибридный детектор активного стриминга:**
     - **Анализ движковых дескрипторов:** Перехват активных `AsyncOperationHandle` в Addressables и активных инстансов `UnityWebRequest`.
     - **Анализ UI-индикаторов прогресса:** Автоматическое считывание динамики значений компонентов `Slider.value` и `Image.fillAmount` на активных модальных окнах загрузки.
   - **Подавление таймера софт-лока (Streaming Keep-Alive):** Пока зафиксирован положительный прирост прогресса ($\Delta p > 0$ за скользящее окно 5000 мс), таймер стагнации замораживается (`STAGNATION_SUPPRESSED_DOWNLOADING`) с максимальным защитным порогом ожидания 120 секунд.
   - **Фиксация зависания CDN (`ASSET_STREAMING_STALL`):** Если индикатор загрузки активен на экране, но прогресс замер на месте ($\Delta p = 0$ в течение $\ge 15$ секунд), либо в консоли перехвачены сетевые ошибки (`HTTP 404/500/503`, `CRC Mismatch`, `RemoteProviderException`) $\rightarrow$ узел помечается дефектом зависания ассетов с заполнением карточки `assetStreamingInfo` (зависший URL, процент, код ошибки).

### 10.8. Технология визуализации: Автономный Vis-Network (HTML Canvas)
- Итоговый отчёт `Docs/QA_Audit_Report.html` компилируется как **единый полностью автономный (Self-Contained) файл** без внешних CDN-зависимостей.
- Граф отрисовывается на высокопроизводительном HTML Canvas через оффлайн-бандл **Vis-Network**:
  - **Санитизация пользовательского ввода (XSS Protection):** Все строковые переменные (названия окон, тексты кнопок, стектрейсы ошибок C#) перед внедрением в DOM и JSON-модель графа пропускаются через функцию санитизации `escapeHtml()`:
    ```typescript
    function escapeHtml(str: string): string {
      return str.replace(/[&<>'"]/g, tag => ({
        '&': '&amp;', '<': '&lt;', '>': '&gt;', "'": '&#39;', '"': '&quot;'
      }[tag] || tag));
    }
    ```
  - **Стабилизация физического движка (Physics Freeze):** Моделирование силовых полей графа отключается после 100 итераций (`network.setOptions({ physics: { enabled: false } })`), предотвращая паразитный 100% троттлинг процессора в браузере.
  - Поддержка зума, панорамирования, физической укладки (Force-Directed Layout) и кластеризации для графов на 1000+ узлов без падения FPS браузера.
  - Цветовая индикация: зеленый — штатный путь; синий — исследованные ветки; **красный пульсирующий** — обнаруженные дефекты и тупики с раскрытием карточки бага по клику.

## 11. ЖИЗНЕННЫЙ ЦИКЛ, СЕТЕВОЙ ПРОТОКОЛ И СИСТЕМА СНИМКОВ (SAVE-STATE ENGINE)

### 11.1. Сетевое рукопожатие (Handshake) и устойчивость к Play Mode
При старте соединения по WebSocket клиент и сервер выполняют строгое версионное рукопожатие:
```json
// Запрос от CoreAgent:
{
  "cmd": "handshake",
  "clientVersion": "2.0.0",
  "clientType": "URDT_CORE_AGENT",
  "sessionToken": "a8f2c31e-4509-42b7-810a-b28669c5e3d1"
}

// Ответ от Unity Server:
{
  "status": "connected",
  "protocolVersion": "2.0.0",
  "engine": "Unity",
  "engineVersion": "2022.3.x",
  "viewport": { "width": 1920, "height": 1080, "dpi": 96 },
  "activeScene": "URDT_2D_TestPolygon",
  "worldRevision": 1
}
```
- **Устойчивость к остановке/перезапуску Play Mode в Unity Editor:**
  - При остановке Play Mode сокет разрывается.
  - CoreAgent **не падает и не завершает процесс**, а переходит в режим ожидания с экспоненциальным реконнектом (500 мс, 1000 мс, 2000 мс).
  - Как только разработчик снова нажал Play, соединение автоматически восстанавливается, выполняется рукопожатие, и сессия возобновляется без перезапуска агентского окружения!
- **Heartbeat:** Каждые 1000 мс шлется пинг `{ "cmd": "ping", "t": timestamp }`. При отсутствии ответа $> 3000\text{ мс}$ сессия инициирует мягкий реконнект.
- **Протокол повторной синхронизации при переподключении (Re-Sync on Reconnect Protocol):**
  1. При обрыве связи Unity-сервер немедленно выполняет локальный `EMERGENCY_RELEASE_ALL_POINTERS`, сбрасывая все виртуальные пальцы для предотвращения «залипших» нажатий.
  2. Сразу после успешного Handshake сервер принудительно отправляет полный снимок сцены (`ForceFullStatePush`) со свежим счетчиком `worldRevision`.
  3. Слой L2 в CoreAgent приостанавливает выполнение текущего BT-узла, проверяет соответствие активного шага HTN-плана фактической сцене и маячкам. Если зафиксировано расхождение (например, сцена была перезапущена вручную), L2 выставляет сигнал `REPLAN_REQUIRED` и регенерирует тактический план с текущего фактического состояния.

### 11.2. Система снимков сохранений и отката (Save-State & Rollback Engine)
Вместо того чтобы блокировать деструктивные ветки игры черными списками, агент использует **систему моментальных слепков состояний (Save-State Engine)**:

```
    [ Состояние игры перед тестом ]
                   │
                   ▼ (URDT: create_save_state)
    [ Сохраненный снимок: "checkpoint_before_shop" ]
                   │
                   ▼
    [ Агент тестирует любые действия ]
    (Покупка предметов, трата монет, удаление профиля,
     проверка логики сброса сохранений)
                   │
                   ▼
    Тест завершен / Сейв испорчен?
    (URDT: rollback_save_state("checkpoint_before_shop"))
                   │
                   ▼
    [ Мир мгновенно вернулся в исходное состояние! ]
```

#### 11.2.1. Контракт перехвата синглтонов и ScriptableObject (`IUrdtSaveable`)
Для корректной работы с реальными архитектурами Unity (Zenject, VContainer, синглтоны, ScriptableObject-хранилища) вводится явный C# контракт:

```csharp
public interface IUrdtSaveable
{
    string SaveStateKey { get; }
    byte[] CaptureState();
    void RestoreState(byte[] stateData);
    void ResetToDefault();
}
```
- Маячок `UrdtSaveStateTarget` автоматически регистрирует все объекты сцены и DI-контейнеров, реализующие интерфейс `IUrdtSaveable`.

#### 11.2.2. Четырехфазный протокол Clean Rollback (Без зависших корутин и твинов)
Просто перезаписать файлы недостаточно: активные асинхронные цепочки продолжат мутировать стейт поверх загруженного сохранения. Процедура отката выполняется строго поэтапно:

1. **Фаза 1: Принудительная зачистка рантайма (Freeze & Kill):**
   - **Глобальная остановка корутин:** Так как вызов `StopAllCoroutines()` работает строго в пределах одного экземпляра `MonoBehaviour`, центральный менеджер `UrdtRuntimeBootstrap` перебирает всех зарегистрированных держателей корутин (`IUrdtCoroutinesHolder`) и активные скрипты сцены:
     ```csharp
     var behaviours = UnityEngine.Object.FindObjectsByType<MonoBehaviour>(FindObjectsSortMode.None);
     for (int i = 0; i < behaviours.Length; i++) {
         if (behaviours[i] != null && behaviours[i] != this) behaviours[i].StopAllCoroutines();
     }
     ```
   - **Подавление висячих колбэков DOTween:** Принудительное уничтожение твинов без вызова завершающих колбэков:
     ```csharp
     #if URDT_DOTWEEN_SUPPORT
     DG.Tweening.DOTween.KillAll(complete: false);
     #endif
     ```
   - **Отмена фоновых задач UniTask:** Отмена всех фоновых задач через системный токен `CancellationTokenSource`.
   - **Выгрузка аддитивных сцен Addressables:** Если сцена была подгружена динамически через Addressables, выполняется выгрузка через `Addressables.UnloadSceneAsync(handle)`.
2. **Фаза 2: Атомарное восстановление дисковых данных:**
   - Перезапись файлов в изолированной тестовой песочнице `Application.persistentDataPath + "/URDT_Sandbox/"` через временный буфер (`Write-Ahead Temporary Swap`) для защиты от повреждения сейвов при крашах.
   - Сброс и восстановление ключей `PlayerPrefs.Save()`.
3. **Фаза 3: Восстановление памяти синглтонов и DI-контейнеров:**
   - Вызов метода `RestoreState()` для всех зарегистрированных компонентов `IUrdtSaveable`.
   - Адаптер DI (`IUrdtContainerAdapter`) сбрасывает дочерние скоупы инъекций (Zenject / VContainer Sub-Containers).
4. **Фаза 4: Мгновенная синхронизация или мягкий перезапуск сцены:**
   - При локальном откате в пределах одного экрана откат завершается за **< 50 мс** без перезагрузки сцены.
   - Если зафиксировано повреждение графа объектов сцены — выполняется страховочная асинхронная перезагрузка через `SceneManager.LoadSceneAsync(currentScene)`.

### 11.3. Детальная спецификация режимов запуска и сценариев оркестрации

Агент аппаратно поддерживает оба критических сценария через CLI-аргументы и протоколы оркестрации:

#### 11.3.1. Сценарий 1: Интерактивный режим разработчика и QA в Unity Editor (`--watch`)
- **Команда запуска:** `npm run start -- --watch --editor-port 9002`
- **Интеграция с официальным Unity MCP:**
  - Внешний ИИ-ассистент (Antigravity IDE / Cursor) использует инструмент Unity MCP `editor_play` для запуска Play Mode.
  - `UrdtRuntimeBootstrap.cs` открывает WebSocket (`ws://127.0.0.1:9002`) и Named Pipe (`\\.\pipe\urdt_fast_ticker`).
  - CoreAgent подключается, считывает маску маячков сцены и запускает цикл тестирования.
- **Интерактивный локальный веб-дашборд:**
  - Открывается веб-интерфейс (`http://localhost:3000`) на базе Vis-Network.
  - Разработчик видит:
    1. Живую анимацию растущего топологического графа приложения.
    2. Положение виртуальных пальцев (`PointerId 1..10`) на экранной проекции.
    3. Текущие тактические рассуждения L2/L3 и детекторы угроз.
- **Устойчивость к циклу редактирования (Play Mode Resilience):**
  - При нажатии `editor_stop` в Unity MCP сокет мягко переходит в `RECONNECTING` без падения Node.js процесса.
  - При повторном `editor_play` агент восстанавливает соединение за < 500 мс и продолжает сессию.

#### 11.3.2. Сценарий 2: Автономный конвейер непрерывной интеграции CI/CD (`--ci`)
- **Команда запуска:** `npm run start -- --ci --max-duration 600 --report-out Docs/QA_Audit_Report.html`
- **Оркестрация через Unity CLI (Batch Mode с виртуальным дисплеем):**
  - Скрипт CI запускает движок без физического монитора, но с сохранением графического конвейера (чтобы работали `GraphicRaycaster` и `CanvasScaler`):
    ```bash
    Unity.exe -batchmode -force-vulkan -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 \
      -projectPath "E:\Projects\URDT" -executeMethod UrdtTestRunner.RunHeadless \
      -urdtPort 9002 -urdtToken "ci-auto-token-xyz" -maxDuration 600
    ```
- **Реализация C# Runner (`UrdtTestRunner.cs`):**
  ```csharp
  using System;
  using UnityEngine;
  #if UNITY_EDITOR
  using UnityEditor;
  #endif

  public static class UrdtTestRunner
  {
      public static void RunHeadless()
      {
          string[] args = Environment.GetCommandLineArgs();
          int port = 9002;
          string token = Guid.NewGuid().ToString("N");
          string handshakePath = null;
          int maxDurationSec = 600;

          for (int i = 0; i < args.Length; i++)
          {
              if (args[i] == "-urdtPort" && i + 1 < args.Length) int.TryParse(args[i + 1], out port);
              if (args[i] == "-urdtToken" && i + 1 < args.Length) token = args[i + 1];
              if (args[i] == "-urdtHandshakeFile" && i + 1 < args.Length) handshakePath = args[i + 1];
              if (args[i] == "-maxDuration" && i + 1 < args.Length) int.TryParse(args[i + 1], out maxDurationSec);
          }

          Debug.Log($"[URDT] Starting Headless Test Runner on port {port} (Timeout: {maxDurationSec}s)...");
          var bootstrap = UrdtRuntimeBootstrap.EnsureInitialized(port, token);
          if (!string.IsNullOrEmpty(handshakePath))
          {
              var info = new UrdtHandshakeInfo {
                  port = bootstrap.BoundPort,
                  pipeName = bootstrap.BoundPipeName,
                  token = token,
                  pid = System.Diagnostics.Process.GetCurrentProcess().Id,
                  status = "READY"
              };
              System.IO.File.WriteAllText(handshakePath, JsonUtility.ToJson(info));
          }

          // Подписка на завершение аудита
          bootstrap.OnAuditFinished += (exitCode) => {
              Debug.Log($"[URDT] Audit finished with exit code: {exitCode}");
  #if UNITY_EDITOR
              EditorApplication.Exit(exitCode);
  #else
              Application.Quit(exitCode);
  #endif
          };
      }
  }
  ```
- **Синхронизация через Handshake Probe:**
  - CoreAgent выполняет периодический опрос (раз в 1000 мс, таймаут 60 сек) до получения ответа `{"status": "READY"}` от Unity, исключая фальстарты во время компиляции шейдеров.
- **Обработка аварийных прерываний (Graceful Shutdown):**
  - При получении сигнала `SIGTERM` (таймаут раннера CI / отмена джобы):
    1. Немедленно отправляется экстренный пакет `EMERGENCY_RELEASE_ALL_POINTERS` в Unity.
    2. Накопленные телеметрические данные, карточки дефектов и топологический граф немедленно сериализуются в файл `Docs/QA_Audit_Report.html`.
    3. Процесс Unity принудительно завершается через сигнал OS.
- **Коды возврата (Exit Codes):**
  - `exit 0`: Тестирование успешно завершено, все контрактные инварианты GDD соблюдены, тупиков и крашей не обнаружено.
  - `exit 1`: Зафиксированы функциональные краши (NRE/Exceptions), критические дефекты навигации (Soft-Locks) или несоответствие GDD-инвариантам.
  - `exit 42`: Запрос мягкого перезапуска процесса (`RECYCLE_REQUESTED`) в рамках регламента гигиены памяти Mono Heap.
- **Двухуровневая гигиена памяти Mono Heap в CI/CD (Two-Tier CI Memory Recycling Protocol):**
  1. **Уровень 1 (Межтестовая зачистка):** После завершения каждой отдельной механики вызывается комбинация `Resources.UnloadUnusedAssets()` + `GC.Collect(GC.MaxGeneration, GCCollectionMode.Forced, true, true)` для очистки временных текстур и ассетов.
  2. **Уровень 2 (Мягкий перезапуск процесса каждые 20 механик — Clean Process Recycle):** Поскольку Mono Virtual Machine в Unity никогда не возвращает выделенную память кучи обратно операционной системе (Mono Heap Fragmentation), длительные прогоны 40+ механик в CI неизбежно приводят к разрастанию процесса и Out-Of-Memory падению. Раннер CoreAgent каждые 20 завершенных механик сохраняет текущий прогресс в `test_progress.json`, отдает сигнал Unity на выход с кодом `exit 42 (RECYCLE_REQUESTED)`, инициирует холодный перезапуск процесса `Unity.exe` и прозрачно возобновляет тестирование с 21-й механики.
- **Мульти-воркерная параллельная изоляция в CI/CD (Multi-Worker Parallel Isolation Protocol):**
  - При запуске параллельной матрицы тестов (например, 4 параллельных воркера на одном CI-сервере с 16 vCPU) использование жестко заданных портов (9002) и статических имен Named Pipes приводит к фатальным коллизиям `EADDRINUSE` и перехвату чужих команд управления.
  - **Регламент динамического связывания портов (Zero-Collision Binding):**
    1. Раннер CoreAgent запускает Unity-инстанс с аргументами: `-urdtPort 0 -urdtHandshakeFile "/tmp/urdt_handshake_{workerId}_{pid}.json"`.
    2. Движок биндится на системный порт 0 (`TcpListener(IPAddress.Loopback, 0)`), операционная система гарантированно выделяет свободный эфемерный порт (диапазон 49152–65535), а C# генерирует уникальный Named Pipe `\\.\pipe\urdt_fast_ticker_{Guid.NewGuid():N}`.
    3. После успешного биндинга `UrdtTestRunner` сбрасывает метаданные подключения (`port`, `pipeName`, `token`, `pid`, `status: READY`) в файл рукопожатия.
    4. CoreAgent опрашивает появление файла рукопожатия, вычитывает фактические порт и пайп, удаляет временный файл и мгновенно подключается без конфликтов.
- **Профиль развертывания в безголовом Linux Docker (Headless Virtual Rendering / SwiftShader):**
  - **Проблема флага `-nographics`:** Запуск Unity с аргументом `-nographics` полностью отключает графический пайплайн. В этом режиме движок не выполняет батчинг канваса, не вызывает `Canvas.willRenderCanvases`, `CanvasScaler` не вычисляет экранные пропорции, а `GraphicRaycaster` возвращает пустой список лучей. В результате ИИ-агент полностью теряет способность обнаруживать интерактивные кнопки UI и кликать по ним.
  - **Решение через Xvfb и софтверный Vulkan (Google SwiftShader / Mesa llvmpipe):**
    В Linux-контейнерах без физического GPU Unity запускается под виртуальным X-сервером:
    ```bash
    xvfb-run --auto-servernum --server-args="-screen 0 1920x1080x24" \
      ./Unity -batchmode -force-vulkan -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 \
      -projectPath "/workspace" -executeMethod UrdtTestRunner.RunHeadless \
      -urdtPort 0 -urdtHandshakeFile "/tmp/urdt_handshake_${CI_JOB_ID}.json" \
      -urdtToken "${CI_JOB_TOKEN}" -maxDuration 600
    ```
    Это сохраняет полную функциональность графического стека Unity UI, расчет трансформаций канваса и рэйкасты при 100% стабильности в headless Docker-среде.
- **Перехват фатальных нативных крашей движка (Post-Mortem Native Crash Watchdog):**
  - **Ограничение C# обработчиков:** Нативные сбои C++ (Access Violation `0xC0000005` в IL2CPP/PhysX, `SIGSEGV` / `SIGBUS` на Linux, C++ Out-Of-Memory, сброс GPU драйвера Metal/Vulkan) моментально уничтожают процесс `Unity.exe` на уровне ОС без вызова `Application.logMessageReceived`. Сокет WebSocket обрывается с кодом `ECONNRESET`.
  - **Протокол вскрытия (Post-Mortem Autopsy):**
    1. Раннер CoreAgent отслеживает событие `child_process.on('exit', (code, signal))`.
    2. Если процесс завершился аварийно (`code !== 0 && code !== 42`), CoreAgent немедленно блокирует повторные попытки реконнекта сокета (предотвращая 60-секундный таймаут пайплайна).
    3. Автоматически локализуется системный журнал движка (`Player.log` / `Editor.log`) по путям платформы (`LocalLow` в Windows, `~/.config/unity3d/` в Linux).
    4. Анализируются последние 200 строк журнала: вычленяется сигнатура падения (`Crash!!!`, блок `========== OUTPUTTING STACK TRACE ==================`, сбойная библиотека `UnityPlayer.dll` / `libil2cpp.so` / `mono-2.0-bdwgc.dll`).
    5. Формируется карточка инцидента `NATIVE_ENGINE_CRASH` с кодом выхода ОС и нативным стектрейсом, вшивается в итоговый отчет `Docs/QA_Audit_Report.html`, и CI завершается с `exit 1`.

## 14. БЕЗОПАСНОСТЬ, ИЗОЛЯЦИЯ И ХАРДЕНИНГ (SECURITY & HARDENING)

Для безопасного развертывания в публичных CI/CD раннерах и рабочих машинах разработчиков реализована эшелонированная защита:

1. **Токенизация локальных сокетов (Port 9002 Authentication):**
   - При старте `UrdtRuntimeBootstrap` генерирует криптографический сессионный токен (`GUID v4` или аргумент `-urdtToken`).
   - Любое входящее соединение WebSocket / Named Pipe обязано передать токен в первом сообщении `handshake`. Неавторизованные запросы мгновенно сбрасываются с кодом сокета `4401 Unauthorized`. Это исключает перехват управления сторонними процессами на хосте.
2. **Изоляция файлов сохранений (Save-State Sandboxing):**
   - Все дисковые манипуляции во время тестовых сессий строго перенаправляются в подкаталог `Path.Combine(Application.persistentDataPath, "URDT_Sandbox")`.
   - Основные файлы сохранений пользователя/разработчика в корне `persistentDataPath` защищены от случайного удаления или порчи.
3. **Защита от XSS и инъекций в HTML-дашборде:**
   - Все динамические данные (имена сцен, тексты кнопок, ошибки компилятора, стектрейсы) подвергаются строгому экранированию через `escapeHtml()` перед записью в автономный бандл `QA_Audit_Report.html`.
4. **Защита промптов Micro-SLM от инъекций (XML Tag Delimitation):**
   - Данные пользовательских текстов интерфейса оборачиваются в изолированные XML-теги `<screen_ui>` и `<beacon_text>`, а системная инструкция явно запрещает исполнение инструкций изнутри этих блоков.

## 15. ПРИЛОЖЕНИЯ (APPENDICES)

### Приложение A: Спецификация сетевых кадров и конвертов (Wire Frame Specifications)

#### 1. Бинарный кадр Named Pipe (27 байт, Физический поток 50 Гц / 20 мс):
Каждый тик непрерывного руления передается плотным бинарным пакетом фиксированного размера (Little-Endian):
```
[Байт 0]      : uint8  cmdType          (0x01 = CONTINUOUS_STEER, 0x02 = RESISTANCE_ACK)
[Байт 1]      : uint8  pointerId        (1..10)
[Байты 2..5]  : uint32 sequenceNumber   (Монотонно возрастающий счетчик)
[Байты 6..9]  : float  screenX          (Физический пиксель X)
[Байты 10..13]: float  screenY          (Физический пиксель Y)
[Байты 14..17]: float  pressure         (0.0 .. 1.0)
[Байты 18..21]: uint32 targetTimestampMs(Отметка времени для квантования)
[Байты 22..25]: uint32 idempotencyKey   (Хэш пакета для защиты от дублей)
[Байт 26]     : uint8  crc8             (Контрольная сумма кадра)
ИТОГО: 27 байт без аллокаций в куче.
```

#### 2. JSON-конверты WebSocket (Тактический и Стратегический поток):

**Конверт команды от CoreAgent к Unity (`CommandEnvelope`):**
