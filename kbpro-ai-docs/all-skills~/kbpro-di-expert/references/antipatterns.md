# Антипаттерны при управлении зависимостями (DI)

Этот справочник описывает запрещенные практики управления зависимостями в проектах KBPro.

---

## 1. Использование глобальных статических Синглтонов (`.Instance`)

### ❌ НЕПРАВИЛЬНО
```csharp
public class MyGameManager : MonoBehaviour
{
    // Запрещено создавать новые глобальные синглтоны через статические свойства Instance!
    public static MyGameManager Instance { get; private set; }

    private void Awake()
    {
        Instance = this;
    }
}
```

### ❓ Почему это плохо
- Жестко связывает код компонентов с конкретным классом менеджера, делая невозможным юнит-тестирование.
- Приводит к скрытым зависимостям и спагетти-коду.
- Затрудняет смену сцен и управление памятью (синглтоны часто остаются в памяти после уничтожения сцены, ссылаясь на мертвые объекты).

###  ПРАВИЛЬНО
Сделайте менеджер обычным классом (или MonoBehaviour), реализующим интерфейс `IService`, и зарегистрируйте его в `ServiceLocator`. Потребители будут запрашивать его через `LazySrv<IMyGameManager>`.

## 2. Разрешение LazySrv.Value в конструкторе класса

### ❌ НЕПРАВИЛЬНО
```csharp
public class CombatSystem : LogicSystem
{
    private LazySrv<ISoundSystem> _sound = new();
    private ISoundSystem _soundCached;

    public CombatSystem()
    {
        // Ошибка: обращение к .Value в конструкторе!
        // Во время конструирования класса локатор может быть еще пуст.
        _soundCached = _sound.Value; 
    }
}
```

### ❓ Почему это плохо
Порядок конструирования C#-классов и инициализации фреймворка не детерминирован. Обращение к локатору в конструкторе с высокой вероятностью выбросит `NullReferenceException` или вернет устаревшую ссылку.

###  ПРАВИЛЬНО
Считывайте значение свойства `.Value` строго во время фазы `Initialize()` или непосредственно при выполнении игрового метода.
```csharp
public override void Initialize()
{
    base.Initialize();
    
    // Безопасное обращение
    _sound.Value.PlaySound("start");
}
```

## 3. Отсутствие вызова Dispose на полях LazySrv

### ❌ НЕПРАВИЛЬНО
```csharp
public class ToolPresenter : IDisposable
{
    private LazySrv<ICameraService> _camera = new();

    public void Zoom() => _camera.Value.ZoomIn();

    public void Dispose()
    {
        // Ошибка: ссылка в _camera не очищена, LazySrv не освобожден
    }
}
```

### ❓ Почему это плохо
`LazySrv` хранит сильную ссылку на объект сервиса. Если долгоживущий сервис был запрошен короткоживущим презентером, ссылка на презентер или его кэш может зависнуть в памяти, предотвращая очистку памяти сборщиком мусора (Garbage Collector).

###  ПРАВИЛЬНО
Всегда вызывайте `.Dispose()` на всех полях `LazySrv` внутри метода `Dispose()` или `OnDestroy()`.
```csharp
public void Dispose()
{
    _camera.Dispose(); // Обнуляет ссылку
}
```

## 4. Связывание с конкретными классами вместо интерфейсов

### ❌ НЕПРАВИЛЬНО
```csharp
// Зависимость от конкретной реализации класса, а не от интерфейса
private LazySrv<SoundSystemImplementation> _sound = new();
```

### ❓ Почему это плохо
Лишает систему гибкости. Вы не сможете заменить звуковую систему на заглушку (Mock) при тестировании или переключить реализацию под другую платформу без изменения кода потребителей.

###  ПРАВИЛЬНО
Всегда запрашивайте абстрактный интерфейс.
```csharp
private LazySrv<ISoundSystem> _sound = new();
```
