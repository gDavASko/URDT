# Свод правил: C# Code Style, SOLID и Clean Architecture

Этот документ регламентирует правила стиля кода, проектирования и чистоты архитектуры для проектов на платформе KBPro.

---

## 1. C# Code Style (Стиль кода)

* **Кодировка файлов**: Строго UTF-8 с BOM (для стабильности отображения кириллицы на Windows и в Obsidian).
* **Один класс на файл**: Имя файла должно полностью совпадать с именем класса/интерфейса, объявленного в нем.
* **Форматирование Allman**: Открывающая фигурная скобка `{` пишется на новой строке с тем же отступом, что и заголовок. Использовать 4 пробела для отступа (не табы).
* **Модификаторы доступа**: Всегда явно указывать модификаторы доступа для всех классов, методов, свойств и полей (например, `private int _value;` вместо `int _value;`).
* **Правила именования**:
  - `PascalCase` — для названий классов, структур, интерфейсов (с префиксом `I`), методов, свойств, перечислений (enum) и их элементов.
  - `_camelCase` — для приватных и защищенных полей класса.
  - `camelCase` — для параметров методов и локальных переменных.
  - `UPPER_SNAKE_CASE` — для констант (`const`) и статических полей только для чтения (`static readonly`).
  - Суффикс `Async` — обязателен для всех асинхронных методов, возвращающих `UniTask` или `Task`.
* **Порядок членов класса**:
  1. Константы (`const`)
  2. Статические поля (`static readonly` / `static`)
  3. Сериализуемые приватные поля (`[SerializeField] private`)
  4. Приватные обычные поля (`private`)
  5. Свойства (`public` / `private` properties)
  6. Инициализация жизненного цикла Unity (`Awake()`, `OnEnable()`, `Start()`)
  7. Кадровые методы Unity (`Update()`, `FixedUpdate()`, `LateUpdate()`)
  8. Публичные методы
  9. Protected и Private методы
  10. Методы очистки жизненного цикла (`OnDisable()`, `OnDestroy()`, `Dispose()`)

## 2. SOLID принципы в Unity & KBPro

### SRP (Single Responsibility Principle) — Единственная ответственность
* **Разделение View и Logic**: Компоненты визуального слоя (`GameComponent`, `UIVBase`, `UIVWindow`) занимаются только отрисовкой, проигрыванием анимаций и звуков. Они не должны рассчитывать логическое состояние, управлять таймерами игры, начислять баллы или работать с сохранением данных.
* **Разделение Logic и Data**: Логические системы (`LogicSystem`, `FlowSystem`) управляют состоянием и правилами игры, но не хранят сессионные данные напрямую (для этого используются `IParameter` и сервисы статистики) и не занимаются рендерингом.
* **Отсутствие God-classes**: Каждый класс должен решать одну узкую задачу. Если класс разрастается свыше 500 строк, его необходимо разделить.

### OCP (Open/Closed Principle) — Открытость / Закрытость
* **Расширение без изменения кода**: Новые механики или поведение должны добавляться созданием новых классов-наследников или реализаций интерфейсов, а не изменением существующего базового кода.
* **Полиморфизм вместо switch/if**: Избегать длинных цепочек проверки типов (`if (x is TypeA) ... else if (x is TypeB)`). Использовать общие методы интерфейсов.
* **Настройка через данные**: Параметры игры должны настраиваться через ScriptableObject-конфиги (`BaseConfig`) или префабы, без необходимости переписывать C# логику.

### LSP (Liskov Substitution Principle) — Подстановка Лисков
* **Вызов base методов**: Переопределенные методы жизненного цикла (`Initialize`, `Startable`, `Dispose`) не должны нарушать работу базового класса. Вызов базового метода должен происходить в строго отведенном месте (`base.Initialize()` в конце, `base.Dispose()` в конце, `base.Startable()` в начале).
* **Запрет на заглушки**: Классы-наследники не должны выбрасывать `NotImplementedException` для методов общего интерфейса, нарушая контракт.

### ISP (Interface Segregation Principle) — Разделение интерфейсов
* **Узкие интерфейсы**: Интерфейсы должны быть специализированными (например, отдельно `IPaused`, отдельно `IUpdatable`, отдельно `IInputUpdateAware`). Не создавайте "универсальные" тяжелые интерфейсы.

### DIP (Dependency Inversion Principle) — Инверсия зависимостей
* **Зависимость от абстракций**: Системы не должны зависеть от конкретных реализаций других систем. Все зависимости должны осуществляться через интерфейсы.
* **Внедрение зависимостей (DI)**: Запрещено инстанцировать зависимые системы через `new` или обращаться к синглтонам (типа `SoundManager.Instance`). Зависимости инжектируются через `[InjectSystems]`, `[InjectComponent]` или разрешаются через `LazySrv<T>`.

## 3. Clean Architecture (Чистая архитектура)

* **Dependency Rule (Направление зависимостей)**: Внутренние слои (бизнес-логика, домен, вычисления) ничего не знают о внешних слоях (UI, графика, Spine, аудио). 
  - *Запрещено*: Импортировать пространства имен `UnityEngine.UI`, `TMPro`, `Spine`, `UnityEngine.Video` в классах `LogicSystem`, `FlowSystem`, `IParameter` или `BaseConfig`.
* **Пассивный View (Passive View)**: Компоненты отображения (`GameComponent`, `UIVBase`) являются "глупыми" исполнителями. Они принимают чистые данные (числа, строки, булевы флаги) и визуализируют их. Они не принимают решений о переходе между состояниями игры.
* **Изоляция внешних фреймворков**: Работа со звуком, сохранением данных или аналитикой ведется строго через интерфейсы-сервисы (`LazySrv<ISoundSystem>`, `LazySrv<IStatisticService>` и т.д.), предоставляемые платформой.

## 4. KISS, YAGNI, DRY

* **KISS (Keep It Simple, Stupid)**: Выбирайте максимально простое и читаемое решение. Избегайте преждевременного усложнения архитектуры (не нужно создавать паттерны ради паттернов).
* **YAGNI (You Aren't Gonna Need It)**: Пишите только тот код, который нужен прямо сейчас. Не оставляйте "заглушек на будущее", неиспользуемых полей и методов.
* **DRY (Don't Repeat Yourself)**: Дублирование кода недопустимо. Если одинаковый блок логики встречается более двух раз, вынесите его в утилитарный класс, extension-метод или общую `LogicSystem`.
