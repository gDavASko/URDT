# Свод правил: Unity Performance & Safety (Производительность и безопасность рантайма)

Этот документ регламентирует требования по оптимизации производительности, памяти, стабильности C# и безопасности рантайма для Unity-проектов в KBPro.

---

## 1. Безопасность C# и рантайма Unity

### Null-проверки Unity-объектов (UnityEngine.Object)
* **Проблема**: С++ часть объектов Unity может быть уничтожена, в то время как C# обертка всё еще существует.
* **Правило**:
  - Всегда используйте явную проверку `if (obj != null)` или `if (obj == null)`.
  - **Запрещено** использовать null-условные операторы и операторы объединения с null для наследников `UnityEngine.Object` (например, `myMonoBehaviour?.DoSomething()` или `var x = targetRenderer ?? fallback`). Это приводит к непредсказуемым ошибкам в рантайме, так как компилятор C# обходит переопределенные операторы сравнения Unity.

### Избегание async void
* **Проблема**: Ошибки в методах с возвращаемым типом `async void` нельзя перехватить через `try-catch`, что приводит к безмолвному падению потока выполнения или зависанию рантайма.
* **Правило**:
  - Все асинхронные методы, не возвращающие значение, должны возвращать `async UniTaskVoid`.
  - Запуск таких методов должен производиться с вызовом `.Forget()` (например, `PlayAnimationAsync(token).Forget()`).
  - *Исключение*: Допускается `async void` в обработчиках событий Unity UI (например, в коллбэках кнопок `button.onClick.AddListener(async () => ...)`), но даже там внутри тела метода рекомендуется оборачивать вызовы в `try-catch`.

### Контроль отмены задач (Cancellation Safety)
* **Правило**:
  - Все асинхронные методы (`UniTask`, `Task`) обязаны принимать `CancellationToken token`.
  - Этот токен должен пробрасываться дальше во все дочерние асинхронные вызовы (особенно в ожидания времени `UniTask.Delay`, загрузки ресурсов или анимации).
  - При возникновении отмены (например, при выходе из модуля) асинхронная задача должна быть немедленно прервана (через вызов `token.ThrowIfCancellationRequested()`), чтобы не оставлять «висящие» в памяти фоновые процессы.

### Предотвращение утечек памяти (подписки UniRx / EventBus / C# Events)
* **Правило**:
  - Любые подписки на `EventBus<T>`, `MessageBroker` или реактивные стримы `UniRx` (`.Subscribe()`) должны сохраняться в `CompositeDisposable` и очищаться в методе `Dispose()` или `OnDestroy()`.
  - Подписки на долгоживущие C# события (`+=`) обязательно должны иметь парные отписки (`-=`) в методах очистки.

### Контроль секретов и учетных данных (Secret Detection) [Blocker]
* **Правило**:
  - В коде, конфигурациях (`BaseConfig`) или текстовых ассетах **категорически запрещено** жестко прописывать пароли, API-ключи, токены авторизации или приватные адреса серверов. 
  - Все подобные данные должны подтягиваться из переменных окружения (в CI/CD) или шифрованных настроек проекта.

### Использование пространств имен Editor в рантайм-скриптах (Editor Usings / Namespaces) [Critical]
* **Проблема**: Наличие директив `using UnityEditor;` или прямое обращение к API редактора (например, `EditorUtility`, `AssetDatabase`, `Selection` и др.) в рантайм-скриптах (не находящихся в специальных папках `Editor`) приводит к фатальной ошибке компиляции (`Build Failed`) при попытке собрать билд игры под мобильные или другие целевые платформы.
* **Правило**:
  - Все директивы `using UnityEditor;` и любые обращения к API редактора в рантайм-файлах должны быть строго обернуты в директивы компиляции `#if UNITY_EDITOR ... #endif`.
  - Предпочтительно полностью выносить вспомогательный код редактора из рантайм-скриптов в отдельные файлы внутри папок `Editor` (или в файлы с суффиксом `.Editor.cs`, если это поддерживается сборкой).

## 2. Оптимизация производительности и памяти (CPU & GC)

### Исключение аллокаций в горячих путях (Update / OnUpdate)
* **Проблема**: Частое выделение памяти в кадровых методах приводит к быстрой фрагментации кучи и частым зависаниям игры из-за сборщика мусора (GC).
* **Правило**:
  - В методах `Update()`, `FixedUpdate()`, `LateUpdate()` и `OnUpdate()` логических систем **запрещено** использовать:
    * **LINQ**-запросы (`.Where`, `.Select`, `.Any` и т.д.).
    * Циклы `foreach` по динамическим коллекциям (используйте классический `for`).
    * **Конкатенацию строк** (выделение новых строк). Для динамического текста используйте структуры типа `ZString` или форматирование TextMeshPro.
    * Вызовы `boxing` (например, неявное приведение значимых типов к `object` при форматировании логов или вызове `Enum.ToString()`).

### Кэширование компонентов (GetComponent)
* **Правило**:
  - Вызовы `GetComponent<T>()`, `GetComponentInChildren<T>()` или `TryGetComponent<T>()` должны выполняться **строго один раз** во время инициализации (`Awake()`, `Start()` или `Initialize()`) с сохранением ссылки в приватное поле.
  - **Категорически запрещено** вызывать `GetComponent` в кадровых методах (`Update()`, `OnUpdate()`).

### Использование TextMeshPro
* **Правило**:
  - Стандартный UI компонент `UnityEngine.UI.Text` запрещен к использованию. Всегда используйте `TextMeshPro` (или `TextMeshProUGUI`) для вывода текста.
  - У TextMeshPro отключайте **Auto Size** (задавайте размер шрифта явно) во избежание дорогостоящего пересчета геометрии меша текста в каждом кадре при обновлении строки.

### Безопасное уничтожение объектов (Runtime Destruction)
* **Правило**:
  - При динамическом уничтожении созданных GameObject-ов в коде представлений (View) должен использоваться безопасный паттерн с проверкой `Application.isPlaying`:
    ```csharp
    if (Application.isPlaying) Destroy(target);
    else DestroyImmediate(target);
    ```
  - Это предотвращает утечки памяти и ошибки в EditMode и при прогоне тестов (Test Runner).

### Блокировка ввода (Input Click-Through)
* **Правило**:
  - При обработке кликов по 3D/2D объектам (в методах `OnMouseDown` или `PointerHandler`) обязательно должна быть проверка на то, не перекрыт ли клик элементами UI (через `EventSystem.current.IsPointerOverGameObject()`).

### Локализация строк
* **Правило**:
  - Запрещено хардкодить русские/английские строки для текстовых UI полей (например, `myText.text = "Запуск модуля"`). Текст должен выводиться строго через сервис локализации `LazySrv<ILocalizationService>` по ключам.

### Безопасность физических триггеров (Physics Safety)
* **Правило**:
  - В методах `OnTriggerEnter`, `OnCollisionEnter` и их 2D аналогах обязательна проверка пришедшего объекта (по тегу, слою или через `TryGetComponent`) перед вызовом логики. Нельзя допускать срабатывания триггера на любой случайный объект.

### Логирование в релизе (Debug.Log)
* **Правило**:
  - В коммитах не должно оставаться **временных/отладочных** вызовов `Debug.Log`, `Debug.LogWarning` или `Debug.LogError`. В мобильных билдах они существенно снижают FPS. Для постоянных диагностических проверок использовать `Debug.Assert` или оборачивать вызовы в `#if UNITY_EDITOR` / `#if DEBUG`.

### Мертвый код (Dead Code) [Minor]
* **Правило**:
  - Не оставлять в коммитах большие закомментированные куски старого кода. Весь ненужный или замененный код должен быть удален (история сохраняется в Git).
