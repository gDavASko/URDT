# Свод правил: Архитектурные принципы платформы KBPro

Этот документ содержит 23 ключевых архитектурных принципа платформы KBPro, которые должны строго проверяться при рецензировании изменений.

---

## 1. Модульность и Изоляция
* **Принцип 1: Изоляция игровых модулей**. Игровые модули (AbstractGameModule) должны быть полностью изолированы друг от друга. Прямые ссылки на компоненты или классы соседних модулей запрещены. Связь между модулями осуществляется только через шину событий `EventBus<T>` или специализированный `IsolatedGameModuleService`.
* **Принцип 2: Оркестрация модуля**. Сам класс игрового модуля выступает только в роли оркестратора (запуск, остановка, конфигурация портов). Вся прикладная игровая логика должна быть делегирована в специализированные системы (`LogicSystem`, `FlowSystem`).

## 2. Жизненный цикл (Lifecycle)
* **Принцип 3: Строгий порядок Initialize**. В переопределенном методе `Initialize()` класса модуля или системы вызов базового метода `base.Initialize()` должен находиться строго в самом конце метода, после того как проинициализированы все локальные зависимости и поля.
* **Принцип 4: Строгий порядок Dispose**. В переопределенном методе `Dispose()` вызов базового метода `base.Dispose()` должен находиться строго в самом конце метода (последней строкой). До вызова `base.Dispose()` необходимо отписаться от всех событий, уничтожить локальные объекты и освободить ресурсы.
* **Принцип 5: Строгий порядок Startable**. В переопределенном методе `Startable()` вызов базового метода `base.Startable()` должен находиться строго в самом начале метода (первой строкой).
* **Принцип 6: Отслеживание завершения модуля**. Перед завершением работы модуля (вызовом коллбэков завершения) в API модуля обязательно должен выставляться флаг завершения стадии через `ModuleStageApi.IsModuleComplete = true`.

## 3. Управление потоком (Data & Control Flow)
* **Принцип 7: Callback Chains вместо Async для логики**. Игровая логика переходов и шагов строится на цепочках коллбэков (callback chains). Использование `async/await` и `UniTask` допускается только для чисто технических асинхронных ожиданий (загрузка Addressables, пауза на N секунд, ожидание завершения визуального твина). Бизнес-логика игры не должна завязываться на асинхронные цепочки тасок.
* **Принцип 8: DOTween Sequence**. При создании анимаций через DOTween необходимо объединять их в Sequence с использованием метода `MakeSequence()`.
* **Принцип 9: Безопасное удаление твинов (SafeKill)**. Все запущенные твины или последовательности (Sequence) должны безопасно уничтожаться при выгрузке/деактивации объекта через `SafeKill()`.
* **Принцип 10: Логические системы без Update**. Системы логики (`LogicSystem`) не должны наследоваться от `MonoBehaviour` и использовать стандартный метод `Update()`. Вместо этого они реализуют интерфейс `IUpdatable` и управляются через общий цикл обновлений платформы.
* **Принцип 11: Исключение Magic Strings**. Строковые константы (ID звуков, ключи аналитики, анимации) запрещено писать текстом. Для полей ID в инспекторе должен использоваться атрибут `[ConstSelector("GroupName")]`, ссылающийся на автогенерируемые группы констант.
* **Принцип 12: Использование автогенерируемых констант**. Файл `Constants.cs` генерируется автоматически платформой. Любое ручное изменение или добавление констант в этот файл запрещено.

## 4. Внедрение зависимостей (Dependency Injection)
* **Принцип 13: Внедрение через атрибуты Inject**. Зависимости между логическими системами внедряются декларативно через атрибут `[InjectSystems]`.
* **Принцип 14: Внедрение компонентов View**. Ссылки на визуальные компоненты (`GameComponent`) внедряются в системы через атрибут `[InjectComponent]`. Прямые вызовы `GetComponent` или `Find` в рантайме для поиска визуального слоя запрещены.

## 5. Доступ к общим сервисам и ресурсам
* **Принцип 15: Доступ к камере**. Доступ к камере сцены осуществляется строго через `ICameraService` (запрашивается через локатор `LazySrv<ICameraService>`). Прямое обращение к `Camera.main` или кэширование камеры вручную запрещено.
* **Принцип 16: Сессионное хранилище**. Для временного хранения данных внутри игровой сессии используется статистика, доступная через `LazySrv<IStatisticService>` с ключами из `Constants.STATISTICSSERVID`.
* **Принцип 17: Персистентное хранилище**. Сохранение прогресса игрока между сессиями (на диск) осуществляется через сервис `BinaryStoreService`.
* **Принцип 18: Передача сложных типов**. Данные, передаваемые между портами модулей или системами, должны быть обернуты в структуру, реализующую интерфейс `IParameter`.
* **Принцип 19: Параметры сессии и очистка**. При сохранении параметров сессии в сервисе статистики, если параметр должен сохраниться при переходе между модулями, необходимо явно указывать флаг `excludeClear: true`.
* **Принцип 20: Рандомизатор событий**. Для обеспечения честного случайного выбора элементов без повторений должен использоваться реестр `Randomizer`, предоставляемый платформой.
* **Принцип 21: SO-конфигурации от BaseConfig**. Все ScriptableObject, хранящие настройки модулей или уровней, должны наследоваться от `BaseConfig`.
* **Принцип 22: Чистые модели данных**. Модели данных, используемые в модуле, должны быть чистыми структурами данных и не иметь внешних зависимостей.
* **Принцип 23: Использование готовой инфраструктуры**. Запрещено писать собственные менеджеры звука, системы локализации, менеджеры сцен или менеджеры ресурсов, если в платформе KBPro уже есть соответствующий сервис, зарегистрированный в ServiceLocator.
