# Паттерн формирования задач — Дев-отдел

> Тип задач: **разработка** по шагам ГДД — функционалы `логика · графика · анимации · эффекты · звуки · озвучка · туторы`.
> Потребитель паттерна: скилл `bitrix-task-json-builder` (и его связка с `bitrix-task-importer`).
> Индекс всех паттернов: [INDEX.md](INDEX.md). Арт, анимация и ГДД формируются **по другим паттернам** — см. индекс.

---

## 1. Назначение

Единый, воспроизводимый способ превратить раздел ГДД в набор **дев-задач**, каждая из которых реально помогает исполнителю сделать работу, а не служит «болотом из букв». Паттерн задаёт: из чего берём материал, как декомпозируем, из чего состоит карточка, как привязываем картинки и как проверяем качество до заведения в трекер.

---

## 2. Исходный документ

- **Источник правды — Google Doc ГДД.** В задачу он попадает не копией, а **живой ссылкой на конкретный раздел** (deep-link с автопроскролом).
- **Получение структуры:** резолвим `DOC_ID` (по URL от пользователя или Drive-поиском по названию), затем строим индекс якорей и манифест картинок.
  - **Основной источник — Google Docs API `documents.get`**: у каждого heading-параграфа берём `paragraphStyle.headingId` (это и есть `h.xxxx`) + текст заголовка + `tabId` вкладки + inline-объекты (позиции картинок). Лимита на размер нет — работает и на больших ГДД.
  - **HTML-экспорт через Drive (`download_file_content`, `exportMimeType: text/html`) — только ЗАПАСНОЙ путь для НЕБОЛЬШИХ доков.** Google режет экспорт Google Docs на ~10 МБ, поэтому на больших ГДД он падает (`service unavailable`/`internal error`); для них экспорт непригоден — обязателен Docs API.
- **Формат deep-link на раздел (с автопроскролом):**
  ```
  https://docs.google.com/document/d/<DOC_ID>/edit?tab=t.<TAB_ID>#heading=h.<HEADING_ID>
  ```
  `?tab=t.<TAB_ID>` **обязателен** для доков с вкладками — без него якорь игнорируется и проскрола к разделу нет; для одновкладочного дока — `tab=t.0`. `<HEADING_ID>` и `<TAB_ID>` берутся из Docs API.
  > **[🚨 КРИТИЧЕСКОЕ ПРАВИЛО ДЛЯ ИИ] НИКОГДА не выдумывайте и не галлюцинируйте `HEADING_ID`** (например, `h.robot_povar` или `h.123`). Настоящие ID генерируются Google Docs как случайные строки (напр., `h.gjdgxs`). Если у вас нет вывода от Docs API или парсера, вы **ОБЯЗАНЫ** использовать явный плейсхолдер (например, `#heading=h.[ТРЕБУЕТСЯ_ID]`) или запросить у пользователя запуск скрипта-индексатора. Выдуманные ID делают ссылку нерабочей (она открывает начало дока).
- **Два артефакта строятся один раз при парсинге:**
  1. **Индекс якорей:** `заголовок → { heading_id, tab_id }`.
  2. **Манифест картинок:** `{ image_id, src, section_heading, step, functional_bucket, doc_position, caption }` (см. §6).
- Документ бывает тяжёлым — структуру тянет **скрипт** через Docs API (постранично) и пишет индекс/манифест во временный файл на диске; тело в контекст модели не тянуть.

## 3. Принципы формирования (декомпозиция)

Главный принцип:

> **Описание задачи = полный контракт результата ДАННОГО специалиста по ДАННОМУ шагу, а не пересказ ГДД.**
> ГДД живёт по ссылке; задача самостоятельно фиксирует, что сдать, какие применимые требования выполнить и как понять, что результат готов.

Правила:

1. **Шаги берутся ИЗ ГДД 1:1.** Один пункт/подраздел/этап ГДД = один шаг. Запрещено выдумывать шаги («каркас», «общий цикл», «обзор»), если их нет в тексте.
2. **Один шаг = одна задача на функционал, никогда не «модуль целиком».** Модуль — это эпик.
3. **Полный набор из 7 на каждый игровой шаг:** `логика · графика · анимации · эффекты · звуки · озвучка · туторы`. Для сервисных экранов набор сокращается по смыслу. Функционал пропускается для шага, только если он реально неприменим (и это помечается).
4. **Разные функционалы → разные тексты.** Совпадение описаний у двух функционалов одного шага — это дефект, а не норма (частая ошибка ИИ — дублировать один текст в 7 задач).
5. **Ссылка не заменяет полноту.** Deep-link даёт контекст, но не отменяет полного описания цели, требований и результата в самой задаче. Копировать весь ГДД дословно не нужно.
6. **Пусто → нет задачи.** Если по функционалу в разделе ГДД реально ничего нет — задача не создаётся (или помечается стабом), а не добивается чужим текстом.
7. **Неоднозначности — в отдельный список «Вопросы по ТЗ», а не в выдуманные задачи.**

**Двухфазность (гейт схемы).** Сначала — дерево-схема `модуль → шаг → 7 функционалов` в файл `<имя_тз>_tasks_schema.md` рядом с источником, с реальным deep-link у каждого шага. Пользователь подтверждает/правит. Генерация JSON — **только после явного аппрува**.

## 4. Функциональная линза

Каждый функционал вытягивает из раздела ГДД **только свой срез**. Это механизм против дублей и против воды.

| Функционал | Берёт (маркеры) | НЕ берёт |
|---|---|---|
| **логика** | правила, состояния, переходы, числа/параметры, условия победы/провала, взаимодействия инструментов, edge-cases | как выглядит/звучит |
| **графика** | экраны, UI-элементы, ассеты, спрайты, состояния объектов, стиль/бренд-бук, макеты | правила, тайминги |
| **анимации** | что и когда движется, триггеры, Spine vs Unity, переходы, длительности | статичный арт, логика |
| **эффекты** | VFX/партиклы: вспышка, свечение, брызги, когда срабатывает | звук, правила |
| **звуки** | SFX и моменты их проигрывания | реплики диктора |
| **озвучка** | реплики/подсказки диктора, фразы персонажей, триггеры | музыка/SFX |
| **туторы** | чему учим, шаги обучения, подсказки, «рука-призрак», порядок жестов | реализация самой механики |

Алгоритм на шаг S с текстом раздела T:
1. Разбить T на атомарные утверждения (предложения/пункты).
2. Пометить каждое функционалом по маркерам.
3. Тело функционала = только его утверждения; общемодульный бойлерплейт (одинаковый для всех шагов) отбрасывается — берётся то, что специфично шагу.
4. Переписать в **императив-результат** («Реализовать состояние заливки 0→100% с событием завершения»), а не факт («в игре есть прогресс-бар»).
5. Из тех же утверждений вывести проверяемый DoD.
6. Пусто → задача не генерируется.

## 5. Состав карточки задачи (4 части)

```
1) Заголовок:   [Dev][<функционал>] <Модуль> — <Шаг>
2) Цель:        полный самостоятельный контракт результата для этого специалиста по этому шагу
3) Ссылка:      📄 Раздел ГДД → https://docs.google.com/document/d/<ID>/edit?tab=t.<TAB_ID>#heading=h.<anchor>
4) Доп. описание:
      Что сделать:   • императив-результат 1 • …   (2–6 пунктов, функционально-специфичные)
      Готово, когда: • проверяемый критерий 1 • …  (DoD)
      Картинки:      [только из этого раздела/функционала по манифесту — см. §6]
```

- **Заголовок** строго `[Dev][<функционал>] <Модуль> — <Шаг>`. `<функционал>` совпадает с тегом функционала в `TAGS`.
- **Оценка достаточности 7–10 считается по частям 2 + 4 БЕЗ ссылки** — описание обязано само доводить разработчика до результата (§8).
- **Достаточность важнее краткости:** описание должно содержать все требования, нужные для реализации и приёмки. Избегайте воды, но не применяйте формальный лимит слов или пунктов, если он приводит к потере требований.
- **Зависимости:** если шаг зависит от предыдущего — первой строкой доп. описания `Зависит от: <TITLE предыдущего шага>`.

## 6. Картинки — привязка по провенансу (строго по ГДД)

Проблема «ИИ пихает картинки рандомно» решается тем, что картинка привязана к **физической позиции в структуре ГДД**, а не к догадке модели.

**Манифест** (строится при парсинге, §2): для каждой картинки фиксируем раздел, шаг, функциональный бакет и позицию в документе.

**Правила привязки:**
- **Шаг** = раздел, в котором картинка физически стоит (между `H_i` и `H_{i+1}` → принадлежит `H_i`).
- **Функционал** = под-раздел (`Логика`/`Графика`/`Анимации`…), если ГДД так структурирован; иначе — по маркерам подписи/окружающего текста (та же линза, §4).
- Картинка из раздела логики → **только** в задачу `логика`; из анимаций → в `анимации`; и т.д.
- **Каждая картинка — ровно в ОДНУ задачу.** Дубли запрещены (кроме случая, когда ГДД сам повторяет изображение).
- Картинку из шага 4.2 **нельзя** ставить в задачи шага 4.1 — только из своего раздела.
- **Только реально присутствующие** в разделе картинки. Ничего не добавлять «по смыслу» из головы.

**Проверка (два уровня, §8):**
- **Детерминированный оракул (скрипт, 0 токенов):** провенанс (`image_id` ∈ множества раздела шага), функционал (из своего бакета), уникальность (нет в двух задачах), без лишних (нет картинок вне раздела). Нарушение → hard fail.
- **LLM-судья (дёшево, только при неоднозначности бакета):** семантическое соответствие картинки функционалу задачи.

## 7. Контракт полей Bitrix

| Поле | Значение/правило |
|------|------------------|
| `TITLE` | `[Dev][<функционал>] <Модуль> — <Шаг>` |
| `DESCRIPTION` | Части 2–4 карточки (полная цель + deep-link + доп. описание + картинки). |
| `TAGS` | `["Dev", "<версия>", "<p1..p5>", "<функционал>"]` — **только** в этом поле, не в тексте. |
| `PRIORITY` | логика → 3; графика/анимации/эффекты → 2; туторы/звуки/озвучка → 1. |
| `GROUP_ID` | `94` |
| `RESPONSIBLE_ID` | `66` |
| `ALLOW_TIME_TRACKING` | `"1"` |
| `UF_TASKS_TASK_1783529349965` | сложность (трудоёмкость) в человеко-днях (1 ч/д = 8 ч), float. ⚠️ Заполнять **только** этим системным UF-именем; `UF_TASK_CAPACITY` через API напрямую **не работает**. |

- **Кодировка файла JSON:** UTF-8 **с BOM** (кириллица корректна при импорте).
- **Способ вставки картинок в Bitrix** (вложение-файл `UF_TASK_WEBDAV_FILES` vs ссылка/`[IMG]` в описании) уточняется через `b24-dev-mcp` на реализации.
- Теги физически проставляет импортёр вторым вызовом (`task.item.update`) — для сборщика прозрачно.

## 8. Оценка и цикл доработки (порог ≥ 7)

**Developer-тест:** «Представь, что ты разработчик и тебе дали эту задачу. Насколько её описания (БЕЗ ссылки) хватает, чтобы выполнить? 0–10». Целевой диапазон — **7–10**. Ниже → доработка.

**Рубрика достаточности (чек-лист → балл, для стабильности дешёвой модели):**

| Критерий | Вес |
|---|---|
| Понятна конкретная цель/результат | 2 |
| Есть конкретика (параметры, состояния, элементы), не общие слова | 3 |
| DoD измеримый | 2 |
| Всё про ЭТОТ функционал, без чужого/общего шума | 2 |
| Нет воды/филлеров/дублей | 1 |

**Якоря шкалы:** 9–10 — сделаю без вопросов и без ГДД; **7–8 — сделаю основное, 1–2 неблокирующих вопроса (минимум)**; 5–6 — не хватает ключевых деталей; 3–4 — только направление; 0–2 — вода/дубль.

**Гейты (оба обязательны):**
- **Гейт достаточности** — балл рубрики ≥ 7.
- **Картиночный гейт** — детерминированная проверка §6 (провенанс/функционал/уник/без лишних). Не зависит от балла достаточности.

**Судья.** Отдельный **изолированный субагент** со свежим контекстом (никогда не сессия воркера). Самовалидация запрещена; **та же семья моделей допустима**, если это изолированный субагент; кросс-семейность предпочтительна, но не обязательна. Вход судьи — **только текст карточки** (без ссылки, без ГДД). Выход — JSON `{ id, score, verdict, missing[], one_fix }`.

**Цикл:**
1. Генерация всех задач.
2. Судья батчем (8–12 задач/вызов) + детерминированный картиночный оракул.
3. `score < 7` или провал картиночного гейта → **таргетная** доработка только этих задач по `missing`/нарушениям.
4. Ре-оценка только доработанных.
5. Потолок — 2 раунда. Остаток `< 7` → флаг человеку, остальные не блокируются.

---

## 9. Экономия токенов

- Судья **не читает ГДД** — только текст карточки → крошечный промпт.
- **Батчинг** задач в один вызов судьи; ответ — массив.
- **Дешёвая модель** судьи; средняя — только для пограничных 6–7 или для доработки.
- **Картиночный гейт детерминирован** — 0 токенов, точная проверка множеств.
- **Ре-оценка только «грязных»** задач, не всего пула.
- **Доработка по `missing`** — точечная правка, не регенерация.

## 10. Анти-паттерны (запрещено)

- ❌ Дословный дамп ГДД в описание; ❌ один и тот же текст в 7 функционалах.
- ❌ Филлеры: «реализовать согласно ТЗ», «сделать качественно», «см. документ».
- ❌ Картинка не из раздела шага; ❌ картинка не того функционала; ❌ дубль картинки в двух задачах; ❌ «декоративная» картинка «по смыслу».
- ❌ Пустой/неизмеримый DoD.
- ❌ Одна задача = целый модуль.
- ❌ Самовалидация (воркер судит свою же сессию).
- ❌ Теги текстом в `DESCRIPTION`.
