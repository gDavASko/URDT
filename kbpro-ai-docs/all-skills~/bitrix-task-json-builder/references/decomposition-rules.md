# Decomposition Rules — извлечение шагов из ТЗ

> Источник правды: [HowToDecomposeTask_ForAI.md → Этап 1.5](../../../../../kbpro-wiki/raw/Architecture/CoreFramework/Guides/HowToDecomposeTask_ForAI.md). Этот файл — рабочая выжимка для скилла.

## Главное правило

Шаги **не придумываются** агентом — они **извлекаются из ТЗ**. ТЗ почти всегда уже разделено на крупные блоки (разделы, нумерованные пункты, под-пункты, этапы, списки требований, таблицы). Эти блоки **и есть** шаги. Работа скилла — внимательно вычитать ТЗ и нарезать задачи строго по его собственной структуре, ничего не выдумывая и не объединяя.

Одна задача = **один пункт/шаг ТЗ**, НЕ целый модуль. Целый модуль («весь модуль стройки дома») — это эпик, а не задача.

## Алгоритм (для каждого модуля)

1. **Вернись к тексту ТЗ.** Не по памяти и не по своей логике — открой соответствующий раздел.
2. **Найди явную структуру**: заголовки, нумерованные пункты, маркированные списки, фразы «этап / шаг / сначала… затем…», таблицы требований. Это готовые границы шагов.
3. **Сопоставь 1:1.** Каждый пункт/под-пункт ТЗ → одна задача. Сохраняй формулировки и порядок ТЗ.
4. **Ничего не теряй и ничего не добавляй.** Все пункты ТЗ покрыты задачами (полнота); шагов, которых в ТЗ нет, не вставляй.
5. **КАЖДЫЙ шаг дроби по функционалу** (см. ниже) — обязательно, per-step.
6. **Неоднозначность → вопрос, а не догадка.** Непонятные/противоречивые/пропущенные места собирай в список «Вопросы по ТЗ» (вне JSON), не маскируй пробел собственной декомпозицией.

## Дробление шага по функционалу (per-step, ПОЛНЫЙ НАБОР, ОБЯЗАТЕЛЬНО)

**Ментальная модель:** каждый шаг/этап — это отдельный экран, на нём есть всё своё. Исполнитель берёт задачу **по шагу** и делает под него ВСЁ (арт, звук, озвучку, тутор, анимации, эффекты, логику). Поэтому у **каждого** шага — **полный набор из 7 функционалов**:

`логика` · `графика` · `анимации` · `эффекты` · `звуки` · `озвучка` · `туторы`.

✅ Правильно: под этапом «Анестезия» → 7 задач `[Dev][логика] Кариес - Анестезия`, `[Dev][графика] …`, `[Dev][анимации] …`, `[Dev][эффекты] …`, `[Dev][звуки] …`, `[Dev][озвучка] …`, `[Dev][туторы] …`. Под этапом «Бор» — свой такой же полный набор.

❌ Запрещено:
- Все «логики» этапов отдельно, а туторы/графика/анимации — общим блоком на модуль.
- `[Dev][графика] Модуль - ассеты модуля` одной задачей на все этапы.
- `[Dev][туторы] Модуль - обучение` одним тутором на весь модуль.
- Пропускать функционал у шага, потому что в ТЗ он описан общим для модуля — дублируем под каждый шаг.

В ТЗ функционал часто описан общим на модуль (шаги похожи) — это НЕ повод делать общую задачу. `DESCRIPTION` функциональной задачи = релевантная этому шагу часть ТЗ. Пропуск функционала у шага допустим только при явной неприменимости (служебный экран) и должен быть помечен.

## Показ схемы (Этап 1.7)

- На показе схемы агент **переключается в plan mode**.
- Схема рисуется **деревом** и **сохраняется в `.md` рядом с исходным ТЗ** (`<имя_тз>_tasks_schema.md`), не только в чат.
- **Каждый функционал — отдельная строка/задача**; **без сокращений** (никаких «[7 функц.]», «…») — полный список целиком.
- **«Каркас»/«обзор»/«общий цикл»** отдельными задачами **не создаём**, если ТЗ явно не требует.
- **Дубли** (шаги, повторяющиеся между модулями) помечаем `🔁` и указываем, где ещё встречаются; реализацию переиспользуем, в `DESCRIPTION` дубля — пометка «Дубль механики …, переиспользовать».
- Итоговый JSON сохраняется **в той же папке, что и ТЗ** (`<имя_тз>_tasks.json`).

## DoD корректной задачи

- ✅ Прямо соответствует конкретному пункту/шагу ТЗ (можно показать пальцем в ТЗ).
- ✅ Один чёткий проверяемый результат.
- ✅ Помещается в заголовок `[Dev][<функционал>] <Модуль> - <Шаг>` (см. правило именования в `field-contract.md`).
- ❌ НЕ «сделать весь модуль / всю систему / всю фичу».
- ❌ НЕ шаг, придуманный агентом и отсутствующий в ТЗ.

## Пример: ТЗ уже задаёт шаги

Раздел ТЗ «4. Строительство дома» с пунктами `4.1 Фундамент · 4.2 Стены · 4.3 Крыша · 4.4 Отделка` →
четыре задачи (Дом — Фундамент, Дом — Стены, Дом — Крыша, Дом — Интерьер), взятые из ТЗ один-в-один.

## Приоритет и зависимости

- `PRIORITY`: Логика = 3, Визуал = 2, остальное = 1.
- Если ТЗ задаёт порядок выполнения — фиксируй зависимость первой строкой блока 1 `DESCRIPTION`: `Зависит от: <TITLE предыдущего шага>`.
